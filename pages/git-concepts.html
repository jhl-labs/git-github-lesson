Git 핵심 개념

Git은 "파일들의 상태를 사진 찍듯 저장하고, 언제든 그 시점으로 돌아갈 수 있게 해주는 도구"입니다. 다음 장 실습실의 미션 9개에서 쓰는 개념을 여기서 순서대로 모두 정리합니다. 명령어를 외우기 전에 머릿속 그림부터 잡고 가요.

🗺️ 이 장의 읽는 법 각 절 제목 옆의 [미션 N]은 그 개념을 직접 쳐 보는 실습실 미션 번호예요. 맨 아래 개념 지도에 미션 ↔ 개념 ↔ 명령을 한 표로 모아 두었습니다.

1. 왜 Git이 필요할까?

이런 폴더, 한 번쯤 만들어 본 적 있죠?

보고서_최종.docx
보고서_최종_수정.docx
보고서_최종_수정_진짜최종.docx
보고서_최종_수정_진짜최종_팀장님피드백반영.docx

Git을 쓰면 파일은 하나로 두고, 변경 기록이 따로 차곡차곡 쌓입니다. 그리고 이 기록 덕분에

  • 📜 언제, 누가, 무엇을, 왜 바꿨는지 알 수 있고
  • ⏪ 망가지면 예전 상태로 되돌릴 수 있고
  • 🌿 원본을 건드리지 않고 새 기능을 따로 실험할 수 있고
  • 👥 여러 명이 동시에 작업한 결과를 합칠 수 있습니다.

2. 저장소 만들기와 첫 설정 [미션 1]

저장소(repository)는 "Git이 기록을 관리하는 폴더"입니다. 평범한 폴더에서 git init을 하면 숨김 폴더 .git이 생기고, 이 .git 안에 모든 커밋과 브랜치 정보가 들어갑니다. .git을 지우면 기록도 사라져요. 

git config --global user.name "홍길동"          # 커밋에 남을 이름 (컴퓨터당 한 번)
git config --global user.email "hong@example.com" # 커밋에 남을 이메일
mkdir my-project && cd my-project
git init                                          # 이 폴더를 저장소로 만들기 → .git 생성
ls -a                                             # .git 이 보이면 성공
  • 왜 이름·이메일부터? 커밋마다 "누가 만들었는지"가 기록되기 때문이에요. 설정하지 않으면 커밋이 거부되거나, 컴퓨터 이름으로 추측한 엉뚱한 이름·이메일이 기록됩니다. GitHub에서는 이메일로 내 계정과 커밋을 연결해요.
  • --global은 "이 컴퓨터의 모든 저장소에 적용", 빼면 "이 저장소에만 적용"입니다.

3. 커밋 = 프로젝트의 스냅샷 [미션 1]

커밋(commit)은 "이 시점의 프로젝트 전체 모습"을 찍은 사진입니다. 커밋마다 고유한 ID(a1b2c3d 같은 해시), 작성자, 시간, 메시지가 붙고, 바로 앞 커밋(부모)을 가리킵니다. 그래서 커밋들은 시간 순서대로 이어진 사슬이 됩니다.

커밋을 가리키는 방법: 해시와 HEAD~N

표기뜻예
a1b2c3d커밋 해시(앞 7자리만 써도 됨)git show a1b2c3d
HEAD지금 내가 서 있는 커밋git show HEAD
HEAD~1, HEAD~2지금보다 1개, 2개 전 커밋 (부모, 조부모)git reset --soft HEAD~1
main, origin/main브랜치 이름도 그 브랜치의 최신 커밋을 가리킴git merge origin/main

git log --oneline은 커밋을 한 줄씩, --all을 붙이면 다른 브랜치의 커밋까지 보여 줍니다.

좋은 커밋 메시지 "수정", "asdf" 대신 무엇을 왜 바꿨는지 한 줄로: 로그인 실패 시 에러 메시지 표시, 엑셀 빈 행 무시하도록 변경

4. 세 개의 공간: 작업 디렉터리 → 스테이징 → 저장소 [미션 1·2]

Git을 처음 배울 때 가장 헷갈리는 부분이지만, 이것만 알면 명령어의 80%가 이해됩니다. 이 사이트는 세 공간을 항상 같은 색으로 표시해요.

왜 바로 커밋하지 않고 스테이징을 거칠까요? 파일 10개를 고쳤어도 "로그인 기능" 관련 3개만 골라서 하나의 커밋으로 만들 수 있게 하려는 거예요. 택배로 치면 스테이징은 상자에 물건을 담는 단계, 커밋은 상자를 테이프로 봉하고 송장을 붙이는 단계입니다.

파일의 4가지 상태와 git status

상태뜻git status에서 보이는 곳다음 행동
UntrackedGit이 아직 모르는 새 파일Untracked filesgit add
Modified커밋된 파일을 고쳤지만 아직 안 담음Changes not staged for commitgit add 또는 git restore
Staged다음 커밋에 들어가기로 담김Changes to be committedgit commit 또는 git restore --staged
Committed저장소에 안전하게 기록됨nothing to commit, working tree clean—

무엇이 바뀌었나: git diff

  • git diff — 작업 디렉터리 ↔ 스테이징 차이 (아직 안 담은 변경)
  • git diff --staged — 스테이징 ↔ 마지막 커밋 차이 (커밋하면 들어갈 변경)
  • +로 시작하는 줄은 추가, -로 시작하는 줄은 삭제예요.

기록하지 않을 파일: .gitignore

비밀번호가 든 .env, 빌드 결과물, 캐시 폴더처럼 저장소에 넣으면 안 되는 파일은 .gitignore에 적어 두면 Git이 아예 무시합니다. .gitignore 파일 자체는 팀원과 공유해야 하니 커밋해요. 단, 이미 커밋한 파일은 나중에 적어도 무시되지 않습니다(먼저 git rm --cached로 추적을 끊어야 해요). 

# .gitignore 예시
secret.env
build/
__pycache__/
*.log

README.md를 수정한 직후, 이 변경은 어디에 있을까요?

정답! 파일을 저장해도 Git은 아직 아무것도 기록하지 않았어요. git add로 스테이징하고 git commit해야 저장소에 남습니다.

5. 브랜치 = 커밋을 가리키는 이름표 [미션 3]

브랜치(branch)는 거창한 복사본이 아니라 특정 커밋을 가리키는 가벼운 이름표예요. 새 커밋을 만들면 지금 있는 브랜치의 이름표가 새 커밋으로 따라 옮겨갑니다. HEAD는 "내가 지금 어느 브랜치에 있는지"를 가리키는 특별한 표시입니다.

명령하는 일
git branch브랜치 목록. *가 붙은 것이 지금 브랜치(HEAD)
git branch 이름브랜치를 만들기만 함 (이동하지 않음)
git switch 이름그 브랜치로 이동 → 작업 디렉터리의 파일이 그 브랜치의 모습으로 바뀜
git switch -c 이름만들고 바로 이동
git merge 이름그 브랜치의 작업을 지금 브랜치에 합침 (먼저 받을 쪽으로 이동!)
git branch -d 이름병합이 끝난 브랜치 삭제 (안 합친 브랜치는 -D로 강제)

브랜치를 옮기면 다른 브랜치에만 있는 파일이 사라진 것처럼 보여요. 지워진 게 아니라 그 브랜치의 커밋에 들어 있을 뿐이니, 돌아가면 다시 나타납니다.

병합의 두 가지 모양: fast-forward vs 병합 커밋

6. checkout과 detached HEAD [미션 4]

예전 Git은 git checkout 하나로 여러 일을 했어요. 너무 헷갈려서 Git 2.23부터 switch(브랜치 이동)와 restore(파일 되돌리기)로 나뉘었지만, 인터넷 자료와 회사 문서에는 여전히 checkout이 많으니 읽을 줄은 알아야 합니다.

checkout 사용법뜻요즘 방식
git checkout 브랜치브랜치 이동git switch 브랜치
git checkout -b 새브랜치만들고 이동git switch -c 새브랜치
git checkout -- 파일파일을 마지막 커밋 상태로 되돌림git restore 파일
git checkout HEAD~1과거 커밋으로 이동 (detached HEAD)git switch --detach HEAD~1

detached HEAD는 HEAD가 브랜치가 아니라 커밋을 직접 가리키는 상태예요. 과거 코드를 "구경"할 때 쓰는 모드입니다. 이 상태에서 커밋을 만들면 어느 브랜치에도 속하지 않아 잃어버리기 쉬워요. 구경이 끝나면 git switch main으로 돌아오고, 그 자리에서 작업을 이어 가고 싶다면 git switch -c 새브랜치로 이름표부터 붙이세요.

7. 충돌(conflict)과 해결 [미션 5]

두 브랜치가 같은 파일의 같은 줄을 서로 다르게 고친 뒤 병합하면, Git은 어느 쪽이 맞는지 판단할 수 없어 멈추고 사람에게 묻습니다. 이것이 충돌이에요. 고장이 아니라 정상적인 협업 과정입니다. 서로 다른 줄이나 다른 파일을 고쳤다면 Git이 알아서 합쳐요. 

<<<<<<< HEAD
오늘의 점심 메뉴: 비빔밥        ← 지금 브랜치(받는 쪽)의 내용
=======
오늘의 점심 메뉴: 돈가스        ← 합치려는 브랜치의 내용
>>>>>>> feature/menu
  1. 충돌 파일 확인 — git status의 "both modified" 파일
  2. 파일 편집 — 남길 내용만 남기고 <<<<<<< ======= >>>>>>> 세 줄을 모두 지우기 (둘 다 남겨도, 새로 써도 됨)
  3. 해결 표시 — git add 파일
  4. 병합 마무리 — git commit → 병합 커밋 생성

병합을 아예 없던 일로 하고 싶다면 git merge --abort로 병합 전 상태로 돌아갈 수 있어요.

8. 로컬 저장소와 원격 저장소 [미션 6]

지금까지는 모두 내 컴퓨터 안의 이야기였어요. 원격 저장소(remote)는 인터넷 너머(GitHub)에 있는 같은 저장소의 사본입니다. 보통 origin이라는 별명으로 부릅니다.

명령하는 일비유
git remote add origin 주소원격 저장소를 origin이라는 별명으로 연결공유 앨범 주소 저장
git push내 커밋을 원격에 올리기내 사진을 공유 앨범에 업로드
git fetch원격의 새 소식만 받아오기 (내 작업은 그대로)앨범의 새 사진 목록 확인
git pullfetch + 내 브랜치에 merge새 사진을 받아 내 앨범에 합치기
git clone 주소원격 저장소 전체를 처음 내 컴퓨터로 복사 (origin 자동 연결)공유 앨범 통째로 다운로드

origin/main — 내 컴퓨터에 있는 "GitHub의 main 사진"

origin/main 같은 원격 추적 브랜치는 "마지막으로 확인했을 때 GitHub의 main이 어디를 가리켰는지"를 기억하는 읽기 전용 이름표예요. GitHub이 바뀌어도 저절로 갱신되지 않고, git fetch(또는 pull)를 해야 최신으로 바뀝니다. 그래서 동료가 push했는데도 git status가 "up to date"라고 말할 수 있어요 — 내 컴퓨터가 아직 소식을 못 들은 거죠.

  • git push -u origin main — 처음 push할 때 -u(upstream)를 붙이면 "내 main ↔ origin/main"이 짝이 되어, 다음부터는 git push, git pull만 쳐도 됩니다.
  • push가 거절(rejected)될 때 — GitHub에 내가 없는 커밋(동료의 push)이 있으면 덮어쓰지 않도록 거절돼요. git pull로 받아 합친 뒤 다시 push하면 됩니다.
  • git branch -a는 내 브랜치와 원격 추적 브랜치(remotes/origin/...)를 함께 보여 줘요.

동료가 GitHub main에 커밋을 올렸습니다. 내 컴퓨터에서 git fetch만 하면 무엇이 바뀔까요?

정답! fetch는 "소식만 받아 오기"예요. 내 브랜치에 합치려면 git merge origin/main을 하거나, 처음부터 git pull(= fetch + merge)을 씁니다.

9. 팀 협업 흐름: clone부터 병합까지 [미션 7]

실무에서는 이미 GitHub에 있는 팀 저장소에 참여하는 경우가 대부분이에요. 흐름은 거의 항상 이렇습니다.

  1. clone — git clone 주소로 전체 기록을 받기. origin이 자동으로 연결돼요.
  2. 기능 브랜치 — main에 직접 커밋하지 않고 git switch -c feature/이름에서 작업·커밋
  3. 브랜치 push — git push -u origin feature/이름. GitHub에 내 브랜치가 생기고, 여기서 PR(Pull Request)을 열어 리뷰를 받아요.
  4. 최신 main 따라잡기 — 그 사이 동료가 main을 바꿨다면 git fetch → git merge origin/main(또는 git pull origin main)으로 내 브랜치에 반영하고 다시 push
  5. 병합 — 리뷰가 끝나면 GitHub의 Merge 버튼으로 main에 합치고, 모두 git pull로 최신 main을 받아요.
왜 브랜치로 일할까? main은 "언제나 동작하는 버전"으로 지키고, 바뀐 내용은 PR에서 사람(과 AI)이 검토한 뒤 들어가게 하기 위해서예요. PART 2의 Step 6에서 진짜 GitHub으로 해 봅니다.

10. 되돌리기: restore · revert · reset [미션 8·9]

되돌리는 명령이 여러 개인 이유는 무엇을(파일? 스테이징? 커밋?) 어디까지 되돌리느냐가 다르기 때문이에요.

상황명령결과
파일을 망쳤다 (아직 add 전)git restore 파일마지막 커밋 상태로 되살림 ⚠️ 수정 내용은 사라짐
실수로 add 했다git restore --staged 파일스테이징에서만 빼기, 파일 수정은 그대로
이미 push한 커밋을 취소하고 싶다git revert 커밋그 커밋을 거꾸로 적용한 새 커밋을 추가. 기록은 그대로라 안전
아직 push 안 한 커밋을 취소하고 싶다git reset [모드] HEAD~1브랜치를 과거로 되감음. 커밋이 기록에서 빠짐

reset의 세 가지 모드

reset은 브랜치 이름표를 과거 커밋으로 되감는 명령이에요. 모드는 "되감고 나서 그동안의 변경을 어느 공간에 남기느냐"만 다릅니다.

모드저장소(커밋)스테이징작업 디렉터리언제 쓰나
--soft되감음변경 남음 ✅변경 남음 ✅커밋 메시지만 다시 쓰고 싶을 때
--mixed (기본값)되감음비워짐변경 남음 ✅커밋을 다시 나눠 담고 싶을 때
--hard되감음비워짐변경 삭제 ⚠️그 변경을 완전히 버릴 때
⚠️ reset vs revert — 황금률 push한 커밋은 revert, 내 컴퓨터에만 있는 커밋은 reset. 이미 공유된 커밋을 reset으로 지우고 다시 push하면 동료들의 기록과 어긋나 큰 혼란이 생깁니다.

방금 만든 커밋의 메시지에 오타가 있어요(아직 push 전). 변경 내용은 그대로 두고 커밋만 다시 하고 싶다면?

정답! --soft는 커밋만 취소하고 변경을 스테이징에 그대로 남겨 바로 다시 커밋할 수 있어요. --hard는 변경까지 버리고, revert는 되돌리는 커밋이 하나 더 쌓입니다.

Git과 GitHub의 관계로 가장 알맞은 것은?

정답! Git은 인터넷 없이도 혼자 쓸 수 있어요. GitHub(또는 GitLab, Gitea 등)는 저장소를 공유하고 협업 기능(이슈, PR, Actions…)을 얹은 서비스입니다.
