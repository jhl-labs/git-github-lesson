GitHub 깊이 알기

Git이 "버전 관리 엔진"이라면 GitHub는 그 위에 사람·권한·리뷰·자동화·보안을 얹은 협업 플랫폼입니다. 이 장은 계정과 권한 구조부터 인증, PR 워크플로우, 브랜치 보호와 rulesets, 보안 기능, gh CLI 활용까지 팀에서 GitHub를 "제대로" 운영하는 데 필요한 지식을 정리합니다.

(참고) 실습에 필요하지 않지만… PART 1·2 실습은 이 장 없이도 진행할 수 있습니다. 실습을 끝낸 뒤 팀 저장소를 설계하거나 권한·보안 설정을 정할 때 참고하는 레퍼런스입니다. GitHub 기능은 플랜(요금제)과 저장소 공개 범위에 따라 달라지고 자주 바뀝니다. 이 장에서 플랜 의존 표시가 붙은 항목은 사용 전 링크된 공식 문서를 꼭 확인하세요.

핵심 용어 한눈에

Organization
여러 사람이 저장소를 공동 소유하는 계정. 팀·역할·정책·결제를 한곳에서 관리합니다.
Repository role
저장소에 대한 권한 단계. Read·Triage·Write·Maintain·Admin.
PAT
Personal Access Token. 비밀번호 대신 쓰는 토큰. classic과 fine-grained 두 종류.
GitHub App
사람이 아닌 "앱"으로 설치되어 저장소별·권한별로 짧게 사는 토큰을 받는 통합 방식.
Ruleset
브랜치·태그·push에 규칙을 거는 차세대 보호 기능. 여러 개를 겹쳐 적용할 수 있습니다.
Required check
병합 전에 반드시 성공해야 하는 CI 작업(status check).

1. 계정, Organization, Team, 저장소 역할

계정의 종류

종류특징
개인 계정 (personal)한 사람. 저장소의 소유자이며 협업자(collaborator)를 초대해 쓰기 권한을 줄 수 있습니다. 세분화된 역할은 없습니다.
Organization공동 소유. 사람은 개인 계정으로 로그인해 조직에 소속됩니다. Team 단위 권한, 조직 정책, SSO(Enterprise) 등을 관리합니다.
Enterprise 계정여러 Organization을 묶어 정책·결제·감사를 통합 관리 (GitHub Enterprise 플랜).

Organization 안의 역할

  • Owner — 조직 전체 관리. 최소 2명을 두어 한 명이 자리를 비워도 잠기지 않게 하는 것이 권장됩니다.
  • Member — 조직 구성원. 기본 저장소 권한(base permission)은 조직 설정으로 정합니다(없음/Read/Write/Admin).
  • Outside collaborator — 조직 구성원이 아니지만 특정 저장소에만 초대된 외부인.
  • 그 외 Billing manager, Security manager, Moderator 등 특수 역할이 있습니다.

Team은 사람을 묶는 단위로, 저장소 권한을 Team에 주면 관리가 쉬워지고 @org/team 멘션·리뷰 요청·CODEOWNERS에 쓸 수 있습니다. Team은 중첩(부모/자식)할 수 있습니다.

저장소 역할 (Organization 저장소)

역할할 수 있는 일 (누적)대상 예시
Read코드 보기·clone, 이슈·PR 작성과 댓글다른 팀, 관찰자
Triage+ 이슈·PR 라벨·담당자 지정, 닫기/다시 열기 (코드 쓰기 불가)이슈 관리 담당
Write+ 브랜치 push, PR 병합, 릴리스 관리개발자
Maintain+ 일부 저장소 설정(토픽, 기능 켜고 끄기 등). 민감한 설정·삭제는 불가프로젝트 리드
Admin+ 모든 설정, 보호 규칙, 접근 권한, 저장소 삭제·이전저장소 관리자

Enterprise Cloud에서는 이 역할들을 조합한 사용자 지정 역할(custom repository roles)도 만들 수 있습니다 플랜 의존. 원칙은 언제나 최소 권한입니다.

2. 저장소 공개 범위

범위누가 볼 수 있나비고
Public인터넷의 누구나많은 유료 기능이 공개 저장소에선 무료. 표준 GitHub-hosted runner도 무료
Private명시적으로 접근 권한을 받은 사람보호 기능 일부가 유료 플랜에서만 동작
Internal같은 Enterprise의 모든 구성원GitHub Enterprise 전용 플랜 의존. 사내 "inner source"용
Private → Public 전환은 되돌리기 어렵다 공개로 바꾸는 순간 전체 커밋 이력이 공개됩니다. 과거에 커밋했다 지운 비밀·개인정보도 이력에 남아 있으면 그대로 노출됩니다. 전환 전 secret scanning과 이력 점검을 하세요. 공개 저장소의 fork는 원본을 다시 private으로 바꿔도 남을 수 있습니다.

3. 인증: 비밀번호 대신 무엇을 쓰나

GitHub.com은 2021년부터 Git 작업에 계정 비밀번호를 받지 않습니다. 대신 아래 방법을 씁니다.

HTTPS + 토큰 / SSH 키 / gh

방식원격 주소장점주의
HTTPS + credential helperhttps://github.com/you/repo.git방화벽 친화적. Git Credential Manager·gh가 브라우저 로그인으로 토큰을 관리토큰을 직접 URL에 넣지 말 것
SSH 키git@github.com:you/repo.git한 번 등록하면 편리, 커밋 서명 키로도 재사용 가능개인키 유출 시 즉시 GitHub에서 삭제
gh auth login둘 다 가능CLI·Git 인증을 한 번에 설정토큰 범위(scope)를 필요한 만큼만
 
# SSH 키 만들기 (ed25519 권장)
ssh-keygen -t ed25519 -C "you@example.com"
# 공개키(~/.ssh/id_ed25519.pub)를 Settings → SSH and GPG keys 에 등록
ssh -T git@github.com            # "Hi you! You've successfully authenticated..."

# gh CLI로 로그인하고 Git의 HTTPS 인증까지 맡기기
gh auth login                    # GitHub.com → HTTPS → 브라우저 로그인
gh auth setup-git
gh auth status                   # 로그인 계정과 토큰 범위 확인

PAT: classic vs fine-grained

classicfine-grained
범위계정이 접근 가능한 모든 저장소에 scope 단위(repo, workflow 등)로 적용한 소유자(사용자 또는 조직)의 리소스로 한정, 그중 특정 저장소만 선택 가능
권한굵은 scope (repo = 모든 private 저장소 읽기/쓰기)항목별 읽기/쓰기 (Contents, Issues, Pull requests, Actions…)
조직 통제조직이 classic PAT 접근을 막을 수 있음조직 소유자가 승인 필수로 설정 가능
만료설정 가능(만료 없음도 가능하나 비권장)만료일 필수(조직 정책으로 최대 기간 제한 가능)

가능하면 fine-grained를 쓰세요. 다만 공식 문서 기준으로 fine-grained PAT는 아직 일부 시나리오를 지원하지 않습니다: 내가 멤버가 아닌 공개 저장소·외부 협업자로 초대된 저장소에 기여하기, 여러 조직에 한 토큰으로 접근, Packages 접근, Checks API 호출, 사용자 소유 Projects 접근 등. 이 목록은 계속 줄어들고 있으니 공식 문서를 확인하세요.

2FA와 패스키

GitHub는 2023년부터 코드를 기여하는 사용자에게 2단계 인증(2FA) 의무화를 단계적으로 적용했습니다. TOTP 앱, 보안 키(WebAuthn), 패스키, GitHub Mobile을 쓸 수 있고, SMS는 가장 약한 수단입니다. 복구 코드는 반드시 오프라인에 보관하세요. 조직은 "구성원 2FA 필수" 정책을 걸 수 있습니다.

GitHub App vs OAuth App (그리고 GITHUB_TOKEN)

GitHub AppOAuth App
누구로 동작앱 자신(봇) 또는 사용자를 대신해서항상 사용자를 대신해서
권한세분화된 권한 + 설치한 저장소에만scope 단위, 사용자가 접근 가능한 전체
토큰 수명설치 토큰(installation access token)은 1시간 후 만료사용자가 취소할 때까지 유효한 경우가 많음
추천새 통합·자동화의 기본 선택"GitHub로 로그인" 같은 단순 사용자 인증

GitHub Actions의 GITHUB_TOKEN도 사실 GitHub App(GitHub Actions 앱)의 설치 토큰입니다. 해당 저장소에만 유효하고 job이 끝나면 만료됩니다. 워크플로우에 permissions:로 필요한 권한만 명시하는 것이 좋습니다(예: PART 2의 contents: write, issues: write). 봇이 장기 PAT를 쓰는 대신 조직용 GitHub App을 만들어 actions/create-github-app-token으로 짧은 토큰을 발급받는 방식이 안전합니다.

4. Fork와 upstream 동기화

fork는 남의 저장소를 내 계정으로 복사한 서버 측 사본입니다. 쓰기 권한이 없는 오픈소스에 기여할 때 쓰며, 내 fork에 push한 뒤 원본(upstream)으로 PR을 보냅니다. 팀 내부 저장소라면 fork 대신 같은 저장소의 브랜치로 PR을 여는 편이 단순합니다. 

gh repo fork upstream-owner/project --clone   # fork + clone + upstream 원격 자동 설정
cd project
git remote -v                # origin = 내 fork, upstream = 원본

# 원본의 최신 변경 반영
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main

# 또는 서버 측에서 바로 (웹의 "Sync fork" 버튼과 동일)
gh repo sync you/project --source upstream-owner/project
fork의 main에서 직접 작업하지 마세요. 항상 기능 브랜치를 만들어 PR을 보내면 upstream 동기화가 fast-forward로 깔끔하게 유지됩니다.

5. Pull Request 워크플로우 깊이 보기

PR 생명주기

  1. Draft PR로 일찍 열기 작업 중임을 알리고 CI를 미리 돌립니다. draft는 병합할 수 없고 CODEOWNERS 리뷰 요청도 자동으로 가지 않습니다. 준비되면 "Ready for review". (private 저장소에서의 draft PR 지원은 플랜 의존)
  2. 설명 작성 무엇을·왜·어떻게 테스트했는지. Closes #12, Fixes #12 같은 키워드를 쓰면 기본 브랜치에 병합될 때 이슈가 자동으로 닫힙니다.
  3. 리뷰 리뷰어는 Comment / Approve / Request changes 중 하나로 제출합니다. Request changes는 보호 규칙에 따라 병합을 막습니다.
  4. 수정 반영 같은 브랜치에 커밋을 push하면 PR이 갱신됩니다. 대화(conversation)는 해결(resolve) 처리합니다.
  5. 병합 필요한 승인과 required check가 모두 충족되면 병합 방식 중 하나로 병합하고, 브랜치를 삭제합니다.

제안된 변경 (suggested changes)

리뷰 댓글에 아래처럼 쓰면 작성자가 버튼 한 번으로 그 수정을 커밋할 수 있습니다. 여러 제안을 모아 한 커밋으로 적용(batch)할 수도 있습니다.

```suggestion
const total = rows.reduce((sum, r) => sum + r.amount, 0);
```

병합 방식 3가지와 이력에 미치는 영향

방식결과 이력장점단점
Create a merge commitPR의 커밋 전부 + 병합 커밋(부모 2개)실제 작업 흐름 보존, PR 단위로 revert -m 1 가능이력이 그물처럼 복잡해짐
Squash and mergePR 전체가 커밋 1개로 합쳐져 main에 추가main 이력이 "PR 1개 = 커밋 1개"로 깔끔PR 내부의 세부 커밋은 main에 남지 않음. 병합 후 같은 브랜치에서 계속 작업하면 충돌이 생기기 쉬움
Rebase and mergePR 커밋들을 main 끝에 새 해시로 재적용, 병합 커밋 없음일직선 이력 + 개별 커밋 보존커밋 해시가 바뀜. 각 커밋이 독립적으로 의미 있어야 함

저장소 설정(Settings → General → Pull Requests)에서 허용할 방식을 고를 수 있습니다. 팀이 일관되게 하나만 쓰는 것이 좋으며, 소규모 팀에는 보통 squash가 무난합니다.

auto-merge와 merge queue

  • auto-merge — "조건이 충족되면 자동으로 병합"을 예약합니다. 필요한 승인과 required check가 정의된 보호 규칙이 있어야 의미가 있습니다. 공개 저장소(Free)와 Pro·Team·Enterprise의 private 저장소에서 사용 가능 플랜 의존.
  • merge queue — 동시에 여러 PR이 병합될 때 "각자는 통과했지만 합치면 깨지는" 문제를 막습니다. 큐에 들어온 PR들을 앞선 PR들과 합친 상태로 다시 CI를 돌린 뒤 순서대로 병합합니다. 공식 문서 기준 조직 소유 공개 저장소, 또는 GitHub Enterprise Cloud 조직의 private 저장소에서 사용 가능합니다 플랜 의존. GitHub Actions 워크플로우는 merge_group 이벤트로 트리거되도록 추가해야 합니다.
on:
  pull_request:
  merge_group:        # merge queue가 만든 임시 브랜치(gh-readonly-queue/...)에서도 CI 실행

6. 브랜치 보호 규칙과 Rulesets

"main에는 리뷰와 CI를 통과한 PR로만 들어온다"를 사람의 약속이 아니라 시스템이 강제하게 만드는 기능입니다.

자주 쓰는 규칙

규칙효과
Require a pull request before merging직접 push 금지, PR 경유 필수. 필요 승인 수 지정
Dismiss stale approvals승인 후 새 커밋이 push되면 기존 승인 무효화
Require review from Code Owners변경된 경로의 CODEOWNERS 승인 필수
Require status checks to pass지정한 CI job 성공 필수. "Require branches to be up to date"로 최신 base 기준 통과도 강제 가능

Branch protection rules vs Rulesets

Branch protection rule (기존)Ruleset (신규)
적용 개수한 브랜치에 하나만 적용여러 ruleset이 겹쳐서 적용, 충돌하면 가장 엄격한 규칙이 이김
대상브랜치브랜치, 태그, push(파일 경로·확장자·크기 제한)
상태켜짐/삭제Active / Disabled 전환 (삭제 없이 끄기). Enterprise에서는 평가 모드도 제공

조직 단위불가Enterprise 플랜에서 조직 전체 저장소에 일괄 적용 가능
플랜 의존: 보호 기능의 사용 가능 범위 공식 문서 기준, protected branches·rulesets·CODEOWNERS·auto-merge·Wiki는 GitHub Free/Free for organizations에서는 공개 저장소에서만, GitHub Pro·Team·Enterprise Cloud에서는 공개·private 저장소 모두에서 사용할 수 있습니다. 즉 무료 플랜의 private 저장소에서는 main 보호를 걸 수 없습니다. 파일 경로·크기 등을 제한하는 push rulesets는 Team 이상 플랜의 private·internal 저장소에서, 조직 전체에 거는 rulesets는 Enterprise 플랜에서 제공됩니다. 7. CODEOWNERS

경로별 책임자를 정해 PR이 열리면 자동으로 리뷰를 요청합니다. 파일 위치는 .github/CODEOWNERS, 저장소 루트, docs/ 중 하나이며, 병합 대상 브랜치에 있는 파일이 기준입니다.

# .github/CODEOWNERS
# 문법은 .gitignore 와 비슷. 아래쪽(나중에 나온) 규칙이 우선한다.
*                       @your-org/maintainers
/converter/             @your-org/data-team
/.github/workflows/     @your-org/devops
*.md                    @you
CODEOWNERS 자체(.github/CODEOWNERS)와 .github/workflows/에도 소유자를 지정하세요. 워크플로우 파일은 저장소 비밀에 접근하는 코드이므로 리뷰 없이 바뀌면 위험합니다. "Require review from Code Owners" 규칙과 함께 써야 실제 강제력이 생깁니다.

9. Releases와 태그

Release는 Git 태그에 릴리스 노트와 첨부 파일(바이너리)을 얹은 GitHub 기능입니다. 태그가 없으면 Release를 만들 때 함께 생성됩니다.

gh release create v1.2.0 --generate-notes            # 이전 태그 이후 병합된 PR로 노트 자동 생성
gh release create v1.3.0-rc.1 --prerelease --notes "테스트용"
gh release create v1.2.0 ./dist/app.zip --title "v1.2.0" --notes-file CHANGELOG.md
gh release list
gh release download v1.2.0 -p "*.zip"
# .github/release.yml — 자동 생성 노트의 분류 규칙
changelog:
  exclude:
    labels: [skip-changelog]
  categories:
    - title: 새 기능
      labels: [feature]
    - title: 버그 수정
      labels: [bug]
    - title: 기타
      labels: ["*"]
이미 공개한 버전의 태그를 다른 커밋으로 옮기지 마세요. 사용자·캐시·패키지 관리자가 같은 이름의 다른 내용을 받게 됩니다. 문제가 있으면 새 PATCH 버전을 내는 것이 원칙입니다.

10. 저장소의 "얼굴": README, LICENSE, CONTRIBUTING, SECURITY.md

파일역할
README.md무엇이고, 어떻게 설치·실행하고, 어디서 도움을 받는지. 저장소 첫 화면에 표시
LICENSE라이선스가 없으면 공개 저장소라도 기본적으로 "모든 권리 보유" — 남이 합법적으로 쓸 수 없습니다. MIT·Apache-2.0 등 선택
CONTRIBUTING.md기여 절차, 브랜치·커밋 규칙, 로컬 테스트 방법. 이슈·PR 작성 화면에 링크됨
CODE_OF_CONDUCT.md커뮤니티 행동 강령
SECURITY.md취약점을 공개 이슈가 아닌 어떤 경로로 제보하는지, 지원 버전
SUPPORT.md, FUNDING.yml지원 채널, 후원 버튼
Wiki저장소와 별도의 Git 저장소(repo.wiki.git)로 관리되는 문서. 코드와 함께 리뷰하고 싶다면 docs/ 폴더가 더 낫습니다 (private 저장소의 Wiki는 플랜 의존)

조직의 .github라는 이름의 공개 저장소에 이 파일들을 두면 해당 파일이 없는 조직 저장소 전체의 기본값으로 쓰입니다. you/you처럼 사용자 이름과 같은 저장소의 README는 프로필 페이지에 표시됩니다.

기능하는 일사용 범위

Private vulnerability reporting / Security advisories외부인이 비공개로 취약점 제보, 관리자가 비공개 fork에서 수정 후 GHSA 공개·CVE 요청공개 저장소
 
# .github/dependabot.yml — Actions 버전과 pip 의존성을 매주 점검
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
  - package-ecosystem: pip
    directory: /converter
    schedule:
      interval: weekly
    groups:
      minor-and-patch:
        update-types: [minor, patch]
push protection이 막았다면 "이건 테스트 키라서 괜찮다"며 우회(bypass)하기 전에, 정말 실제 키가 아닌지 확인하세요. 실제 키라면 커밋을 고쳐(git commit --amend 또는 rebase -i) 비밀을 제거하고, 이미 다른 곳에 노출됐을 가능성이 있다면 키를 폐기하세요. 비밀은 코드가 아니라 Actions Secrets·환경 변수·비밀 관리 도구로 공급합니다.

보안 기능의 제품 구성(GitHub Secret Protection, GitHub Code Security 등)과 가격은 자주 바뀝니다. GitHub 보안 문서를 확인하세요.

gh api: REST·GraphQL 직접 호출

gh가 인증을 처리해 주므로 토큰을 다루지 않고 API를 바로 호출할 수 있습니다. {owner}, {repo}는 현재 디렉터리의 저장소로 자동 치환됩니다.

# 저장소 정보에서 필요한 필드만 (--jq 는 jq 문법)
gh api repos/{owner}/{repo} --jq '{name, visibility, default_branch}'

# 페이지네이션 자동 처리: 모든 이슈 제목
gh api --paginate 'repos/{owner}/{repo}/issues?state=all&per_page=100' --jq '.[].title'

# POST: 이슈에 라벨 추가 (-f 문자열, -F 타입 추론)
gh api -X POST repos/{owner}/{repo}/issues/12/labels -f 'labels[]=processed'

# 활성 rulesets 확인
gh api repos/{owner}/{repo}/rulesets --jq '.[] | {name, enforcement}'

# GraphQL
gh api graphql -f query='
  query { viewer { login repositories(first: 5, orderBy:{field:UPDATED_AT, direction:DESC}) { nodes { name } } } }'

# 남은 API 호출 한도
gh api rate_limit --jq '.resources.core'

13. Codespaces

브라우저(또는 VS Code)에서 바로 쓰는 클라우드 개발 환경입니다. 저장소의 .devcontainer/devcontainer.json으로 언어 런타임·확장·포트 포워딩을 정의해 두면 누구든 같은 환경을 몇 분 안에 띄울 수 있어 교육·온보딩에 특히 유용합니다. 

{
  "name": "dashboard",
  "image": "mcr.microsoft.com/devcontainers/python:3.12",
  "features": { "ghcr.io/devcontainers/features/node:1": {} },
  "postCreateCommand": "pip install -r converter/requirements.txt",
  "forwardPorts": [8000],
  "customizations": { "vscode": { "extensions": ["ms-python.python"] } }
}
플랜 의존: 무료 사용량 개인 계정에는 월 무료 사용량이 있습니다(공식 플랜 문서 기준 Free: 120 core-hours·15GB 저장, Pro: 180 core-hours·20GB). core-hour는 "코어 수 × 시간"이라 4코어 머신을 1시간 쓰면 4 core-hours가 차감됩니다. 멈춘 codespace도 저장 용량은 계속 차감되니 안 쓰는 것은 삭제하세요. 조직 저장소의 codespace는 조직 결제 설정을 따릅니다. (Codespaces 과금)

14. GitHub Packages와 Container registry

npm, Maven, NuGet, RubyGems, 컨테이너 이미지 등을 GitHub에 게시하는 패키지 저장소입니다. 컨테이너 이미지는 ghcr.io/소유자/이미지 주소를 씁니다. Actions에서는 GITHUB_TOKEN에 packages: write 권한만 주면 별도 토큰 없이 게시할 수 있습니다. 

permissions:
  contents: read
  packages: write
steps:
  - uses: actions/checkout@v6
  - uses: docker/login-action@v3
    with:
      registry: ghcr.io
      username: ${{ github.actor }}
      password: ${{ secrets.GITHUB_TOKEN }}
  - uses: docker/build-push-action@v6
    with:
      push: true
      tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
  • 패키지 공개 범위는 저장소와 별도로 설정할 수 있습니다. 공개 패키지는 무료이며, private 패키지 저장 용량은 플랜별로 다릅니다 플랜 의존.
  • 배포에는 latest 같은 변경 가능한 태그보다 이미지 digest(@sha256:…)로 고정하는 것이 재현성과 보안에 좋습니다.
  • 공식 문서상 fine-grained PAT는 아직 Packages 접근을 지원하지 않으므로, 로컬에서 게시할 때는 write:packages scope의 classic PAT가 필요할 수 있습니다.

회사 동료 3명이 GitHub Free 조직의 private 저장소를 씁니다. "main에는 리뷰 승인 + CI 통과한 PR만 병합"을 강제하고 싶습니다. 어떻게 해야 할까요?

정답! 공식 문서 기준 Free 플랜의 보호 규칙·rulesets는 공개 저장소에서만 동작합니다. CODEOWNERS는 리뷰 "요청"만 자동화할 뿐, 강제하려면 보호 규칙의 "Require review from Code Owners"가 필요합니다. 공개 저장소로 운영해도 된다면 Free에서도 가능합니다.

PR 10개를 하루에 병합하는 저장소에서 "Squash and merge"를 쓰면 main 이력은 어떻게 될까요?

정답! squash는 PR의 변경 전체를 하나의 새 커밋으로 만들어 main에 붙입니다. (a)는 merge commit 방식, (b)는 rebase 방식과 비슷하지만 rebase and merge도 해시는 새로 만들어집니다.
