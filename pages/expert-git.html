Git 깊이 알기

add·commit·push만으로도 일은 됩니다. 그런데 "커밋이 사라졌어요", "rebase 하다 꼬였어요", "Windows에서만 diff가 전부 바뀌어요" 같은 순간이 오면 Git이 내부에서 무엇을 저장하고 어떻게 가리키는지 알아야 침착하게 해결할 수 있습니다. 이 장은 객체 모델에서 출발해 병합·되돌리기·협업 전략·복구 레시피까지 실무자의 시야로 정리합니다.

(참고) 실습에 필요하지 않지만… PART 1·2를 진행하는 데 이 장은 필요하지 않습니다. 실습을 마친 뒤 "왜 이렇게 동작하지?"가 궁금할 때, 또는 실무에서 막혔을 때 찾아보는 레퍼런스로 쓰세요. 처음부터 끝까지 읽기보다 오른쪽 목차에서 필요한 절로 바로 이동하는 것을 권합니다.

핵심 용어 한눈에

객체(object)
Git 데이터베이스의 최소 단위. blob·tree·commit·tag 네 종류이며, 내용의 해시가 곧 이름입니다.
ref
커밋 해시에 붙인 사람이 읽을 수 있는 이름. 브랜치·태그·원격 추적 브랜치가 모두 ref입니다.
HEAD
"지금 내가 서 있는 곳". 보통 브랜치를 가리키고(symbolic ref), 브랜치가 커밋을 가리킵니다.
index
스테이징 영역의 실체인 .git/index 파일. 다음 커밋이 될 tree의 설계도입니다.
reachable
어떤 ref에서 부모를 따라가 닿을 수 있는 객체. 닿지 않는 객체는 결국 gc로 지워집니다.
merge base
두 브랜치의 가장 가까운 공통 조상. 3-way merge의 기준점입니다.

1. 객체 모델: Git은 "내용 주소 파일시스템"이다

Git의 저장소(.git/objects)는 거대한 키-값 저장소입니다. 값을 넣으면 그 내용의 해시가 키로 돌아오고(content-addressed), 같은 내용은 몇 번을 넣어도 같은 키 하나로 저장됩니다. 그래서 파일 1,000개 중 1개만 바꿔 커밋해도 나머지 999개는 새로 저장되지 않습니다.

객체담는 것비유
blob파일 내용만. 파일 이름·권한은 없음종이 한 장
tree디렉터리 한 단계: (모드, 이름, blob/tree 해시) 목록폴더의 목차
commit최상위 tree 해시, 부모 커밋 해시(0~N개), author·committer, 메시지목차에 붙인 날짜·서명·설명
tag (annotated)대상 객체 해시, 태그 이름, tagger, 메시지, (선택) 서명특정 판본에 붙인 공식 라벨

직접 들여다보기: git cat-file -p

아무 저장소에서나 따라 해 보세요. 출력 해시는 저장소마다 다릅니다.

# 1) HEAD 커밋 객체를 그대로 출력
git cat-file -p HEAD
# tree d8a1e44...
# parent 4b7e0d9...
# author you <you@example.com> 1731200000 +0900
# committer you <you@example.com> 1731200000 +0900
#
# 로그인 화면 추가

# 2) 커밋이 가리키는 tree 보기 (HEAD^{tree} = HEAD 커밋의 tree)
git cat-file -p 'HEAD^{tree}'
# 100644 blob 3b18e51...    README.md
# 040000 tree 91ac0f2...    src

# 3) 객체 종류와 크기
git cat-file -t HEAD          # commit
git cat-file -s HEAD:README.md  # 바이트 수

# 4) 내용을 직접 객체로 만들어 보기 (저장 없이 해시만 계산)
echo 'hello' | git hash-object --stdin
# ce013625030ba8dba906f756967f9e9ca394464a  ← 어느 컴퓨터에서나 같은 값

해시는 "blob 6\0hello\n"처럼 "종류 + 크기 + 널 문자 + 내용"을 해시한 값입니다. 객체 파일은 zlib으로 압축되어 .git/objects/ce/013625…처럼 앞 두 글자를 디렉터리 이름으로 써서 저장됩니다(이것을 loose object라고 부릅니다).

왜 커밋 해시가 "위조 방지"가 되나 커밋은 tree 해시와 부모 해시를 포함하고, tree는 blob 해시를 포함합니다. 과거 파일 한 글자를 바꾸면 그 blob → tree → 커밋 → 이후 모든 커밋의 해시가 바뀝니다. 그래서 "이력을 고쳤다"는 사실이 반드시 드러나며, 이것이 rebase 후 push --force가 필요한 이유이기도 합니다.

SHA-1과 SHA-256 전환

  • Git은 원래 SHA-1(40자 16진수)을 씁니다. 2017년 SHAttered로 SHA-1 충돌이 실증된 뒤 Git은 충돌 탐지 기능이 있는 SHA-1DC 구현을 기본으로 사용하고 있습니다.
  • SHA-256(64자) 저장소는 git init --object-format=sha256으로 이미 만들 수 있지만, 두 형식 사이의 상호운용(interop)은 아직 개발 중이라 SHA-1 저장소와 SHA-256 저장소는 서로 push/fetch할 수 없습니다.
  • Git 프로젝트는 다음 메이저 버전(Git 3.0)에서 새 저장소의 기본값을 SHA-256으로 바꾸는 것을 BreakingChanges 문서에 예고했지만, 출시일은 정해져 있지 않습니다.
  • GitHub는 현재 SHA-256 저장소를 호스팅하지 않습니다. GitHub에 올릴 저장소는 기본값(SHA-1) 그대로 만들어야 합니다. 상태가 바뀔 수 있는 항목이니 사용 전 공식 문서를 확인하세요.

2. ref, HEAD, detached HEAD

브랜치는 "커밋 해시 하나를 적어 둔 텍스트 파일"에 불과합니다. 그래서 브랜치를 만드는 비용은 사실상 0입니다.

cat .git/HEAD                 # ref: refs/heads/main   ← HEAD는 브랜치를 가리킴
git rev-parse main            # main이 가리키는 커밋 해시
git symbolic-ref HEAD         # refs/heads/main
git show-ref                  # 모든 ref와 해시 목록
git for-each-ref --sort=-committerdate refs/heads/ \
  --format='%(refname:short) %(committerdate:relative)'   # 최근 작업한 브랜치 순
ref 경로의미
refs/heads/*로컬 브랜치
refs/remotes/origin/*원격 추적 브랜치. fetch 때만 갱신되는 "마지막으로 본 원격의 모습"
refs/tags/*태그
refs/stashstash 목록의 맨 위
refs/pull/123/headGitHub가 PR마다 만들어 주는 ref (git fetch origin pull/123/head로 받기 가능)

ref가 많아지면 Git은 개별 파일 대신 .git/packed-refs 한 파일에 모읍니다. 최신 Git은 대규모 저장소용 reftable 형식(git init --ref-format=reftable)도 지원합니다.

상대 참조 문법

표기뜻
HEAD~3첫 번째 부모를 따라 3단계 위
HEAD^2병합 커밋의 두 번째 부모(병합되어 들어온 쪽)
main@{1}reflog 기준, main이 직전에 가리키던 커밋
main@{yesterday}어제 시점의 main (로컬 reflog 기준)
@{u} / @{push}현재 브랜치의 upstream / push 대상
A..BB에는 있고 A에는 없는 커밋 (git log origin/main..HEAD = 아직 push 안 한 커밋)
A...B대칭 차집합. git diff A...B는 "merge base 대비 B의 변경" = PR 화면의 diff
:/fix login메시지에 "fix login"이 들어간 가장 최근 커밋

detached HEAD

HEAD가 브랜치가 아니라 커밋 해시를 직접 가리키는 상태입니다. 태그나 과거 커밋을 체크아웃하면 이렇게 됩니다. 이 상태에서도 커밋은 만들어지지만, 다른 곳으로 이동하는 순간 그 커밋을 가리키는 이름이 없어 "고아"가 됩니다. 

git switch --detach v1.2.0    # 의도적으로 detached 상태 진입
# ...실험 커밋...
git switch -c experiment       # 지금 위치에 브랜치 이름을 붙여 살리기
# 이미 떠났다면: git reflog 에서 해시를 찾아 git branch experiment <해시>

3. index(스테이징 영역)의 실체

.git/index는 "다음 커밋의 tree"를 평평하게 펼친 목록입니다. 각 항목에 경로, blob 해시, 모드, 그리고 파일의 stat 정보(크기·수정 시각 등)가 들어 있어 git status가 모든 파일을 다시 해시하지 않고도 변경 여부를 빠르게 판단합니다. 

git ls-files --stage          # 100644 3b18e51... 0	README.md   (마지막 숫자는 stage 번호)
git ls-files -s src/          # 특정 경로만
git diff                      # 작업 디렉터리 vs index
git diff --staged             # index vs HEAD  (= 다음 커밋에 들어갈 내용)
git add -p                    # 변경을 hunk 단위로 골라 스테이징

충돌이 나면 같은 경로가 index에 stage 1(공통 조상)·2(ours)·3(theirs)로 세 번 기록됩니다. git show :1:path, :2:path, :3:path로 각각 꺼내 볼 수 있고, 충돌을 해결하고 git add하면 stage 0 하나로 합쳐집니다.

4. packfile, gc, maintenance

loose object가 쌓이면 Git은 이것들을 packfile(.git/objects/pack/*.pack + .idx)로 묶습니다. 비슷한 객체끼리는 delta 압축(한 객체를 다른 객체와의 차이로 저장)을 적용합니다. Git은 논리적으로는 스냅샷을 저장하지만, 물리적으로는 이렇게 차이를 저장해 용량을 줄입니다. push/fetch로 오가는 데이터도 packfile 형식입니다. 

git count-objects -vH         # loose/pack 객체 수와 용량
git gc                        # 압축 + 오래된 unreachable 객체 정리
git maintenance start         # 백그라운드 정기 유지보수 예약 (prefetch, commit-graph, 증분 repack 등)
git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n | tail -5   # 가장 큰 객체 찾기
gc가 지우는 것과 지우지 않는 것 reachable 객체와 reflog가 아직 기억하는 객체는 지우지 않습니다. 기본 설정에서 reflog 항목은 도달 가능한 경우 90일, 도달 불가능한 경우 30일 동안 유지되고(gc.reflogExpire, gc.reflogExpireUnreachable), 어떤 ref에서도 닿지 않는 loose object는 기본 2주의 유예 기간(gc.pruneExpire)이 지난 뒤 삭제됩니다. 즉, 실수로 잃어버린 커밋은 대부분 한동안 되살릴 수 있습니다.

5. reflog: "사라진" 커밋 되살리기

reflog는 HEAD와 각 브랜치가 어디를 가리켰는지의 로컬 이동 기록입니다. reset --hard, 잘못된 rebase, 브랜치 삭제 후에도 대부분 여기서 찾을 수 있습니다. 단, reflog는 내 컴퓨터에만 있고 push되지 않습니다. 

git reflog                    # HEAD@{0}: reset: moving to HEAD~3
                              # HEAD@{1}: commit: 결제 모듈 리팩터링   ← 이걸 살리고 싶다
git reflog show feature/pay   # 특정 브랜치의 이동 기록

git branch rescue HEAD@{1}    # 그 지점에 브랜치를 붙여 보존
git reset --hard HEAD@{1}     # 또는 현재 브랜치를 그 지점으로 되돌리기

# reflog에도 없다면(예: 다른 사람이 만든 커밋, 오래된 stash): 도달 불가능한 객체 검색
git fsck --lost-found         # dangling commit/blob 목록, .git/lost-found 에 복사

6. 병합(merge)의 내부

fast-forward vs 병합 커밋

main이 feature의 조상이라면 Git은 새 커밋 없이 main 이름표를 앞으로 옮기기만 합니다(fast-forward). 두 브랜치가 갈라졌다면 부모가 두 개인 병합 커밋을 만듭니다. 

git merge feature             # 가능하면 fast-forward, 아니면 병합 커밋
git merge --no-ff feature     # 항상 병합 커밋 (기능 단위를 이력에 남기고 싶을 때)
git merge --ff-only feature   # fast-forward 불가하면 실패 (pull 기본값으로도 추천)
git config --global pull.ff only

3-way merge와 merge base

Git은 두 끝(M2, F2)만 비교하지 않고 공통 조상 B까지 세 지점을 비교합니다. 한쪽만 바꾼 부분은 그 변경을 채택하고, 양쪽이 같은 부분을 다르게 바꿨을 때만 충돌로 표시합니다. 그래서 "충돌이 났다" = "같은 줄 근처를 양쪽이 고쳤다"입니다. 

git merge-base main feature   # B의 해시
git diff main...feature       # B 이후 feature에서 바뀐 것만 (PR diff와 같은 관점)
git config --global merge.conflictStyle zdiff3   # 충돌 표시에 공통 조상(base) 내용도 함께 보여 줌

ort 전략

Git 2.34부터 기본 병합 엔진은 ort("Ostensibly Recursive's Twin")입니다. 이전 기본값 recursive를 다시 구현해 rename이 많은 큰 저장소에서 훨씬 빠르고, 병합 도중 작업 트리를 건드리지 않고 결과를 메모리에서 계산합니다. Git 2.50부터 -s recursive는 ort의 별칭이 되었습니다 (merge-strategies 문서).

옵션효과
-X ours / -X theirs충돌한 hunk만 한쪽을 자동 채택 (충돌 안 난 상대 변경은 그대로 반영)
-s ours상대 브랜치 내용을 완전히 무시하고 병합 기록만 남김 (전혀 다른 의미이니 주의)
-X ignore-all-space공백 차이를 무시하고 병합
-s octopus3개 이상 브랜치를 한 번에 병합 (충돌이 없을 때만)
같은 충돌을 반복해서 푸는 중이라면: rerere git config --global rerere.enabled true를 켜면 Git이 "이 충돌은 이렇게 해결했다"를 기억했다가 같은 충돌이 다시 나면 자동으로 적용합니다. 장기 브랜치를 자주 rebase할 때 특히 유용합니다.

7. rebase: 이력을 다시 쓰기

git rebase main은 현재 브랜치의 커밋들을 main 끝에 하나씩 다시 적용(cherry-pick)합니다. 내용은 같아도 부모가 바뀌므로 새 해시의 새 커밋이 생깁니다. 결과는 병합 커밋 없는 일직선 이력입니다. 

git switch feature
git rebase main               # feature의 커밋을 main 위로 옮김
# 충돌 시: 파일 수정 → git add 파일 → git rebase --continue
#          포기: git rebase --abort   (rebase 시작 전으로 완전 복귀)

git pull --rebase             # 원격 변경 위에 내 로컬 커밋을 다시 쌓기
git rebase --onto main old-base feature   # old-base 이후 feature 커밋만 main 위로 이식

interactive rebase: 커밋 다듬기

git rebase -i HEAD~4
# 편집기가 열림 (위가 오래된 커밋)
# pick   a1b2c3d 로그인 폼
# squash e4f5a6b 오타 수정        ← 바로 위 커밋에 합치고 메시지도 합침
# fixup  c7d8e9f 린트            ← 합치되 메시지는 버림
# reword 0a1b2c3 API 연결        ← 메시지만 수정
# (drop: 커밋 삭제, edit: 그 커밋에서 멈춰 수정, 줄 순서 변경 = 커밋 순서 변경)

# 나중에 합칠 커밋을 미리 표시해 두는 습관
git commit --fixup a1b2c3d
git rebase -i --autosquash main   # fixup! 커밋이 자동으로 제자리에 배치됨

# 쌓아 올린(stacked) 브랜치들의 이름표도 함께 옮기기 (Git 2.38+)
git rebase -i --update-refs main

merge vs rebase, 그리고 황금률

mergerebase
이력 모양실제로 일어난 그대로(갈라짐·합쳐짐)일직선, 읽기 쉬움
기존 커밋보존(해시 불변)새 커밋으로 교체(해시 변경)
충돌 해결병합 시 한 번다시 적용되는 커밋마다 날 수 있음
공유 브랜치안전위험 — 다른 사람의 이력과 어긋남
황금률: 다른 사람이 이미 가져간 커밋은 rebase하지 않는다 공유된 커밋을 rebase하고 강제 push하면, 동료의 로컬에는 옛 커밋이, 원격에는 새 커밋이 있어 같은 변경이 두 번 들어가거나 작업이 사라집니다. 내 PR 브랜치처럼 나만 쓰는 브랜치는 자유롭게 rebase해도 됩니다. 강제 push가 필요하면 반드시 git push --force-with-lease를 쓰세요. 원격이 내가 마지막으로 본 상태와 다르면(누군가 그 사이 push했다면) 거부되어 남의 커밋을 덮어쓰지 않습니다.

rebase 전·후를 비교하려면 git range-diff main@{1} main feature@{1} feature처럼 range-diff를 쓰면 "커밋 단위로 무엇이 달라졌는지"를 볼 수 있습니다.

8. cherry-pick

다른 브랜치의 특정 커밋의 변경만 현재 브랜치에 새 커밋으로 복사합니다. 핫픽스를 릴리스 브랜치에 옮길 때 자주 씁니다.

git cherry-pick 3f2a9c1                 # 한 개
git cherry-pick -x 3f2a9c1              # 메시지에 "(cherry picked from commit ...)" 기록 → 추적 용이
git cherry-pick A^..B                   # A부터 B까지 범위
git cherry-pick -m 1 <병합커밋>          # 병합 커밋을 가져올 때 기준 부모 지정
git cherry-pick --continue | --abort
같은 변경이 두 브랜치에 서로 다른 해시로 존재하게 되므로, 나중에 두 브랜치를 병합하면 Git이 대개 알아서 처리하지만 이후 그 코드를 다시 고친 경우 충돌이 날 수 있습니다. 가능하면 "먼저 main에 고치고 → 릴리스 브랜치로 cherry-pick" 한 방향으로만 흐르게 하세요.

9. 되돌리기: revert vs reset, restore vs switch

revert — 이력을 보존하며 취소

git revert <커밋>은 그 커밋의 변경을 반대로 적용한 새 커밋을 만듭니다. 이미 push한 커밋을 취소하는 유일하게 안전한 방법입니다.

git revert 3f2a9c1
git revert -m 1 <병합커밋>     # 병합 커밋 되돌리기: 1번 부모(main 쪽)를 기준으로
git revert --no-commit A..B     # 여러 커밋을 하나의 revert 커밋으로
병합을 revert한 뒤 다시 병합하면 변경이 안 들어온다? 병합 커밋을 revert해도 "그 브랜치의 커밋들은 이미 병합됐다"는 이력은 남습니다. 같은 브랜치를 다시 병합하면 Git은 새 커밋만 가져오므로, 먼저 revert 커밋을 revert한 뒤 병합해야 합니다.

reset — 브랜치 이름표를 옮기기

git reset <커밋>은 현재 브랜치가 가리키는 커밋을 옮기고, 옵션에 따라 index와 작업 디렉터리까지 맞춥니다.

모드브랜치(HEAD)index(스테이징)작업 디렉터리대표 용도
--soft이동유지유지최근 커밋 몇 개를 합쳐 다시 커밋 (변경은 스테이징된 채 남음)
--mixed (기본)이동대상 커밋으로 초기화유지커밋·스테이징 취소, 파일 변경은 보존
--hard이동초기화초기화(커밋 안 된 변경 소실)완전히 그 시점으로 되돌리기
--keep이동초기화로컬 변경이 충돌하면 중단--hard의 안전한 대안
reset --hard로 날아간 커밋은 reflog로 살릴 수 있지만, 한 번도 커밋·스테이징하지 않은 작업 디렉터리 변경은 Git이 기록한 적이 없어 되살릴 수 없습니다. 실행 전 git stash 습관을 들이세요.

restore / switch vs checkout

예전의 git checkout은 "브랜치 이동"과 "파일 되돌리기"라는 전혀 다른 두 일을 했습니다. Git 2.23에서 이를 나눈 switch와 restore가 추가되었습니다.

하고 싶은 일새 명령옛 명령
브랜치 이동git switch maingit checkout main
브랜치 만들며 이동git switch -c featgit checkout -b feat
작업 디렉터리 변경 버리기git restore app.jsgit checkout -- app.js
스테이징 취소(파일은 유지)git restore --staged app.jsgit reset HEAD app.js
특정 커밋의 파일 버전 가져오기git restore --source=HEAD~2 app.jsgit checkout HEAD~2 -- app.js

이미 main에 push되어 동료들도 pull 한 커밋에 버그가 있습니다. 가장 적절한 취소 방법은?

정답! 공유된 이력을 다시 쓰는 reset·rebase는 동료의 로컬 이력과 어긋납니다. revert는 "취소 커밋"을 새로 추가하므로 이력이 앞으로만 진행되어 안전합니다.

10. stash: 작업을 잠시 치워 두기

git stash push -m "로그인 WIP"   # 수정·스테이징된 tracked 파일 보관
git stash push -u                 # untracked 파일까지 (-a: ignored 파일까지)
git stash push -p                 # hunk 단위로 골라서 보관
git stash list                    # stash@{0}: On main: 로그인 WIP
git stash show -p stash@{1}       # 내용 확인
git stash apply stash@{1}         # 적용(목록에 남김)
git stash pop                     # 적용 + 목록에서 제거 (충돌 시엔 제거하지 않음)
git stash branch wip-login        # stash를 만든 커밋에서 새 브랜치를 만들어 적용

stash는 내부적으로 특수한 커밋입니다. 실수로 drop했더라도 출력된 해시나 git fsck --unreachable | grep commit으로 찾아 git stash apply <해시>할 수 있습니다.

11. bisect: 버그를 만든 커밋 이진 탐색

"지난주엔 됐는데 지금은 안 된다"면 커밋이 1,000개여도 약 10번(log₂1000)의 테스트로 범인을 찾습니다.

git bisect start
git bisect bad                 # 현재(HEAD)는 버그 있음
git bisect good v1.4.0         # 이 태그 시점엔 정상
# Git이 중간 커밋을 체크아웃 → 테스트 → good / bad 응답 반복
git bisect good   # 또는 git bisect bad, 판단 불가면 git bisect skip
git bisect reset               # 끝나면 원래 브랜치로 복귀

# 자동화: 스크립트가 0이면 good, 1~127(125 제외)이면 bad, 125면 skip
git bisect start HEAD v1.4.0
git bisect run npm test

12. 태그와 SemVer

lightweight 태그annotated 태그
정체커밋을 가리키는 ref일 뿐tag 객체(작성자·날짜·메시지·서명 가능)
만들기git tag v1.0.0git tag -a v1.0.0 -m "첫 릴리스"
용도개인용 임시 표시릴리스. git describe 기본 대상
 
git tag -a v1.2.0 -m "엑셀 다중 시트 지원"
git tag -s v1.2.0 -m "..."           # 서명된 태그
git push origin v1.2.0               # 태그는 기본으로 push되지 않음
git push --follow-tags               # 현재 push하는 커밋에 달린 annotated 태그만 함께
git describe --tags                  # v1.2.0-5-g3f2a9c1 (태그 이후 5커밋, 현재 해시)
git push origin :refs/tags/v1.2.0    # 원격 태그 삭제 (이미 배포된 태그는 옮기지 않는 것이 원칙)

유의적 버전(SemVer)은 MAJOR.MINOR.PATCH 규칙입니다. 하위 호환이 깨지면 MAJOR, 호환되는 기능 추가는 MINOR, 호환되는 버그 수정은 PATCH를 올립니다. 1.0.0-rc.1처럼 프리릴리스 표기도 가능하며, 0.y.z는 "아직 공개 API가 안정되지 않음"을 뜻합니다.

13. worktree: 한 저장소, 여러 작업 폴더

stash나 두 번째 clone 없이, 같은 저장소의 다른 브랜치를 별도 폴더에 동시에 체크아웃합니다. 객체 DB는 공유하므로 빠르고 가볍습니다.

git worktree add ../hotfix -b hotfix/login main   # ../hotfix 폴더에 새 브랜치로 체크아웃
git worktree list
git worktree remove ../hotfix
git worktree prune                                 # 수동으로 지운 폴더의 기록 정리

같은 브랜치를 두 worktree에서 동시에 체크아웃할 수는 없습니다. 긴 빌드나 리뷰를 돌려 두고 다른 작업을 하거나, AI 코딩 에이전트 여러 개를 브랜치별로 병렬 실행할 때 유용합니다.

14. submodule vs subtree

submodulesubtree
저장 방식상위 저장소는 하위 저장소의 커밋 해시(포인터)만 기록 (.gitmodules)하위 프로젝트의 파일을 상위 저장소에 복사해 합침
clonegit clone --recurse-submodules 필요일반 clone으로 끝
장점버전 고정이 명확, 저장소가 가벼움사용자가 존재를 몰라도 됨
단점업데이트 절차가 번거롭고 "detached HEAD" 상태가 흔함상위로 변경을 되돌려 보내기(split/push)가 복잡
 
git submodule add https://github.com/you/shared-lib libs/shared
git submodule update --init --recursive
git submodule update --remote libs/shared    # 하위 저장소의 추적 브랜치 최신으로

git subtree add --prefix=libs/shared https://github.com/you/shared-lib main --squash
git subtree pull --prefix=libs/shared https://github.com/you/shared-lib main --squash
공유 코드가 정식 패키지(npm, PyPI 등)로 배포될 수 있다면 둘 다보다 패키지 의존성이 대개 더 단순합니다.

15. hooks: 이벤트마다 스크립트 실행

hook시점예시 용도
pre-commit커밋 메시지 입력 전lint, 포맷, 비밀 키 탐지
commit-msg메시지 작성 후Conventional Commits 형식 검사
pre-pushpush 전송 전빠른 테스트
post-checkout, post-merge체크아웃·병합 후의존성 재설치 알림
pre-receive, update서버 측정책 강제 (GitHub.com에서는 대신 rulesets 사용)

.git/hooks/는 버전 관리되지 않아 팀과 공유되지 않습니다. 저장소 안의 폴더를 쓰려면 git config core.hooksPath .githooks를 쓰거나, pre-commit·husky 같은 도구를 씁니다.

클라이언트 hook은 git commit --no-verify로 건너뛸 수 있습니다. 반드시 지켜야 하는 규칙은 hook이 아니라 CI(GitHub Actions) + 브랜치 보호/rulesets로 강제하세요. hook은 "빨리 알려 주는 친절", CI는 "통과해야 하는 문"입니다. 
#!/bin/sh
# .githooks/commit-msg — Conventional Commits 형식 간단 검사
if ! head -1 "$1" | grep -Eq '^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: .+'; then
  echo "커밋 메시지는 'type(scope): 설명' 형식이어야 합니다." >&2
  exit 1
fi

16. .gitattributes: 줄바꿈(CRLF/LF), 바이너리, LFS

줄바꿈 문제가 생기는 이유

Windows는 줄 끝에 CRLF(\r\n), macOS·Linux는 LF(\n)를 씁니다. 설정이 제각각이면 한 줄도 안 고쳤는데 파일 전체가 바뀐 diff가 생기고, 셸 스크립트가 /bin/sh^M: bad interpreter로 실패합니다. PART 2의 워크플로우처럼 windows-latest runner에서 checkout·커밋하는 경우에도 이 문제가 나타날 수 있습니다(Git for Windows는 설치 시 보통 core.autocrlf=true를 권장값으로 설정).

개인 설정(core.autocrlf)에 기대지 말고, 저장소에 .gitattributes를 두어 규칙을 고정하는 것이 정답입니다.

# .gitattributes
* text=auto eol=lf          # 텍스트로 판단되면 저장소엔 LF, 체크아웃도 LF
*.bat  text eol=crlf        # Windows 전용 스크립트는 CRLF
*.ps1  text eol=crlf
*.sh   text eol=lf
*.xlsx binary               # 엑셀은 바이너리: 줄바꿈 변환·텍스트 diff·병합 금지
*.png  binary
*.json text eol=lf linguist-generated=true   # GitHub diff에서 생성 파일로 접기
# .gitattributes를 추가한 뒤 기존 파일을 새 규칙으로 정규화
git add --renormalize .
git commit -m "chore: 줄바꿈 규칙 정규화"

git ls-files --eol          # 파일별 index/작업 디렉터리 줄바꿈과 적용된 속성 확인
바이너리 파일의 diff·병합 binary는 -text -diff -merge의 축약입니다. xlsx처럼 ZIP 기반 문서는 Git이 의미 있는 diff를 만들 수 없어 충돌 시 "어느 한쪽 파일 전체"를 골라야 합니다. 그래서 PART 2에서는 엑셀 원본이 아니라 변환된 JSON을 커밋해 변경을 추적 가능하게 만든 것입니다. diff= 드라이버와 textconv로 바이너리를 텍스트로 변환해 diff를 보는 방법도 있습니다.

Git LFS

Git은 모든 버전의 모든 파일을 clone할 때 받아 오므로, 큰 바이너리(영상, 데이터셋, 디자인 파일)를 자주 바꾸면 저장소가 급격히 무거워집니다. Git LFS는 저장소에는 작은 포인터 파일만 커밋하고 실제 내용은 별도 LFS 저장소에 둡니다. 

git lfs install
git lfs track "*.psd"        # .gitattributes 에 "*.psd filter=lfs diff=lfs merge=lfs -text" 추가
git add .gitattributes design.psd
git commit -m "chore: psd를 LFS로 관리"
git lfs ls-files
git lfs migrate import --include="*.psd" --everything   # 이미 커밋된 파일을 LFS로 이전(이력 재작성!)

GitHub의 LFS 저장 용량·대역폭은 플랜과 과금 설정에 따라 다르므로 공식 문서를 확인하세요.

17. 커밋 서명

커밋의 author 이름·이메일은 누구나 아무 값으로나 설정할 수 있습니다(git config user.email). 서명은 "이 커밋을 정말 이 키의 소유자가 만들었다"는 증명입니다. GitHub는 등록된 키로 검증되면 커밋 옆에 Verified 배지를 표시합니다. 

# SSH 키로 서명 (Git 2.34+) — 이미 GitHub용 SSH 키가 있다면 가장 간단
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true
# GitHub Settings → SSH and GPG keys 에서 같은 공개키를 "Signing Key" 유형으로 추가

git log --show-signature -1   # 로컬 검증 (SSH는 gpg.ssh.allowedSignersFile 설정 필요)

GPG 키(gpg.format openpgp, 기본값)나 S/MIME(X.509)도 쓸 수 있습니다. 웹 UI에서 만든 커밋과 GitHub Actions의 일부 커밋은 GitHub의 키로 서명됩니다. 브랜치 보호/rulesets의 "Require signed commits"로 서명을 강제할 수 있습니다.

18. 브랜치 전략

전략구조잘 맞는 경우주의점
GitHub Flowmain + 짧은 기능 브랜치 → PR → 리뷰·CI → 병합 → 배포웹 서비스처럼 지속 배포, 배포 버전이 하나main이 항상 배포 가능해야 하므로 CI·리뷰가 탄탄해야 함
Git Flowmain(릴리스) + develop + feature/release/hotfix 브랜치설치형 SW·모바일 앱처럼 버전 릴리스 주기가 있고 여러 버전을 유지보수브랜치가 많아 병합 비용이 큼. 지속 배포에는 과함
Trunk-based모두가 trunk(main)에 하루 1회 이상 작은 단위로 병합. 미완성 기능은 feature flag로 숨김숙련된 팀, 높은 배포 빈도, 강한 자동 테스트feature flag 관리, 테스트 자동화 수준이 전제

고민된다면 GitHub Flow로 시작하세요. 이 강의의 실습도 GitHub Flow입니다. 장기 브랜치는 오래 살수록 충돌이 커지므로, 어떤 전략이든 브랜치 수명을 짧게 유지하는 것이 핵심입니다.

19. 커밋 메시지 규칙: Conventional Commits

<type>(<scope>): <설명>        ← 50자 안팎, 명령형/현재형

20. 큰 저장소 다루기: shallow·partial clone, sparse-checkout

기법명령받지 않는 것적합한 곳
shallow clonegit clone --depth 1 URL오래된 커밋 이력CI 빌드 (actions/checkout 기본값이 fetch-depth: 1)
blobless clonegit clone --filter=blob:none URL과거 버전의 파일 내용(필요할 때 지연 다운로드)개발자 PC — 이력 탐색은 가능하면서 빠름
treeless clonegit clone --filter=tree:0 URL과거 tree와 blob한 번 빌드하고 버리는 환경
sparse-checkoutgit sparse-checkout set --cone apps/web libs/ui(받긴 하되) 작업 디렉터리에 펼치지 않는 폴더모노레포에서 일부만 작업
 
git clone --filter=blob:none --sparse https://github.com/you/monorepo
cd monorepo
git sparse-checkout set --cone apps/dashboard
git fetch --unshallow          # shallow 저장소를 전체 이력으로 확장
shallow clone에서는 git describe, git log 범위 계산, 변경 파일 비교(git diff origin/main...HEAD)가 실패하거나 틀린 결과를 낼 수 있습니다. CI에서 이런 명령을 쓴다면 actions/checkout에 fetch-depth: 0(전체 이력)을 지정하세요.

21. 상황별 복구 레시피

상황해결
마지막 커밋 메시지를 고치고 싶다 (push 전)git commit --amend -m "새 메시지"
마지막 커밋에 파일 하나를 빠뜨렸다 (push 전)git add 빠진파일 && git commit --amend --no-edit
방금 커밋을 취소하되 변경은 남기고 싶다git reset --soft HEAD~1
main에 실수로 커밋했다 (push 전) — 브랜치로 옮기기git branch feature && git reset --hard origin/main && git switch feature
엉뚱한 브랜치에서 작업 중(커밋 전)git stash && git switch 올바른브랜치 && git stash pop (또는 바로 git switch — 충돌이 없으면 변경이 따라옴)
reset --hard 했더니 커밋이 사라졌다git reflog → git reset --hard HEAD@{n}
브랜치를 지웠다git reflog에서 마지막 해시 찾기 → git branch 이름 <해시>
rebase가 엉망이 됐다 (진행 중)git rebase --abort
rebase를 끝냈는데 결과가 이상하다git reset --hard ORIG_HEAD (또는 git reflog에서 rebase 시작 전 지점)
병합 충돌을 그만두고 싶다git merge --abort
push한 커밋을 취소해야 한다git revert <해시> → 일반 push
push가 rejected (non-fast-forward)git pull --rebase로 원격 변경을 받아 쌓은 뒤 push. 무작정 --force 금지
파일 하나를 특정 커밋 시점으로 되돌리기git restore --source=<해시> 경로
실수로 추적된 파일을 무시하고 싶다.gitignore에 추가 + git rm --cached 경로 (파일 자체는 남음)
비밀번호·키를 커밋해 push했다1순위: 즉시 키 폐기·재발급. 그다음 git filter-repo로 이력에서 제거 후 강제 push, GitHub 지원팀에 캐시된 뷰 삭제 요청 검토. 이미 clone·fork된 사본은 회수 불가
누가 이 줄을 언제 바꿨나git blame -w -C 파일, 줄 범위의 전체 이력은 git log -L 10,20:파일
코드에서 문자열이 추가/삭제된 커밋 찾기git log -S "함수이름" --oneline (pickaxe)
작업 디렉터리를 완전히 깨끗하게git clean -nd로 미리보기 → git clean -fd (되돌릴 수 없음)
이력 재작성 도구는 filter-repo Git 공식 문서도 git filter-branch 대신 별도 도구인 git filter-repo를 권장합니다. 이력 재작성은 모든 해시를 바꾸므로 팀원 전원이 다시 clone해야 합니다. 그리고 유출된 비밀은 이력을 지워도 이미 유출된 것입니다 — 키 폐기가 항상 먼저입니다.

팀원이 Windows에서 .sh 파일을 커밋한 뒤 Linux CI에서 bad interpreter: /bin/sh^M 오류가 납니다. 재발을 막는 가장 좋은 방법은?

정답! .gitattributes는 저장소와 함께 버전 관리되므로 누가 어떤 OS·설정으로 clone하든 같은 규칙이 적용됩니다. 개인 설정은 빠뜨리기 쉽고, CI에서 고치는 것은 증상만 가립니다.
