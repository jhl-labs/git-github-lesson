오늘 만들 서비스

"엑셀로 관리하는 매출 데이터를 팀원들이 웹에서 보게 해 주세요." — 실무에서 정말 흔한 요청입니다. 서버 한 대 없이 GitHub만으로 이걸 만들어 봅니다.

📚 시작 전 이론: 서버 없이 서비스가 돌아가는 원리

이번 PART 2는 화면 속 흉내가 아니라 진짜 GitHub에서 진짜로 실행되는 프로젝트입니다. Step 1~6을 시작하기 전에 "누가, 어디서, 언제 일하는지" 큰 그림을 먼저 잡아 두면 각 Step에서 길을 잃지 않아요.

이벤트 기반 자동화
"이슈가 열렸다", "push 됐다" 같은 사건(이벤트)이 생길 때만 정해 둔 작업이 실행되는 방식. 평소에는 아무것도 돌지 않아요.
Runner
GitHub Actions의 작업을 실제로 실행하는 컴퓨터. 이번 실습의 windows-latest는 GitHub이 클라우드(Azure)에서 job마다 새로 만들어 주는 실제 Windows 서버(VM)입니다.
정적 사이트
미리 만들어 둔 파일(HTML·JS·JSON)을 그대로 내려주기만 하는 웹사이트. 서버 프로그램이 없어도 됩니다.
배포용 브랜치
사람이 고치는 소스(main)와 봇이 만든 결과물(docs)을 브랜치로 나눠 관리하는 방법.
바이브 코딩
AI(Claude Code)에게 목표와 제약을 말로 설명해 코드를 만들게 하고, 사람은 결과를 읽고·실행하고·판단하는 개발 방식.

보통의 웹 서비스 vs 오늘의 구조

보통 "엑셀을 올리면 웹에서 보여주는 서비스"를 만들려면 24시간 켜져 있는 서버, 업로드 API, 데이터베이스가 필요합니다. 오늘은 이 역할을 GitHub 기능으로 나눠 맡깁니다.

보통 서비스의 구성 요소오늘 대신 쓰는 것차이점
업로드 화면 + APIIssues (파일 첨부)GitHub 로그인·권한 확인을 GitHub이 대신 해 줌
항상 켜진 처리 서버Actions runner일이 있을 때만 새 VM이 켜지고, 끝나면 삭제됨
데이터베이스Git 커밋 (docs 브랜치의 data.json)변경 이력이 자동으로 남지만, 검색·동시 수정에는 약함
웹 서버GitHub Pages파일만 내려줄 수 있음 → 진짜 로그인 불가 (한계 장)

runner는 진짜 컴퓨터예요

이슈를 등록하면 GitHub은 클라우드에 방금 설치를 마친 깨끗한 Windows 서버를 한 대 만들어, 여러분 저장소의 코드를 내려받고 워크플로우에 적힌 명령(파이썬 설치, 엑셀 변환, git push…)을 실제로 실행합니다. 일이 끝나면 그 서버는 통째로 폐기돼요. 그래서 다음 실행 때는 이전 실행의 파일이 하나도 남아 있지 않고, 남기고 싶은 결과는 반드시 커밋 같은 방법으로 저장소에 보내야 합니다.

데이터가 흘러가는 순서

  1. 사람이 이슈에 엑셀을 첨부해 등록 → GitHub에 issues: opened 이벤트 발생
  2. 이벤트에 맞는 워크플로우가 깨어나고, GitHub이 Windows runner(VM)를 새로 준비
  3. runner가 첨부 파일을 내려받아 xlwings(안 되면 openpyxl)로 읽고 data.json 생성
  4. 봇 계정(github-actions[bot])이 docs 브랜치에 커밋·push
  5. 이어지는 deploy job이 docs 브랜치 내용을 Pages에 배포 → 브라우저가 data.json을 내려받아 차트로 그림
✅ 실습 전 셀프 체크
  • "runner는 어디에 있는 어떤 컴퓨터이고, 일이 끝나면 어떻게 되는지" 설명할 수 있나요?
  • 이 서비스에 "항상 켜진 서버"가 없는데도 동작하는 이유를 말할 수 있나요?
  • main과 docs 브랜치에 각각 무엇이 들어가는지 구분할 수 있나요?

전체 구조

왜 이런 구조일까?

요구 사항사용하는 GitHub 기능배우는 개념
엑셀 파일을 쉽게 올리고 싶다Issues (파일 첨부 + 이슈 템플릿)이벤트(이슈 생성)가 자동화를 깨운다
엑셀을 사람 손 없이 변환하고 싶다Actions + Windows runner + xlwings(안 되면 openpyxl)워크플로우, 트리거, runner, 권한
변환 결과를 버전 관리하고 싶다Git (docs 브랜치에 커밋)브랜치의 다른 용도: 배포용 브랜치
웹에서 보고 싶다Pages (deploy job이 docs 브랜치 내용을 배포)정적 호스팅
아무나 보면 안 된다비밀번호 화면 (JavaScript)…그런데 이게 진짜 보안일까? → 마지막 장
🤔 왜 Windows + xlwings? xlwings는 실제 Microsoft Excel 프로그램을 원격 조종해서 파일을 읽습니다. 수식·매크로가 많은 회사 엑셀을 "엑셀이 보여주는 그대로" 읽을 수 있다는 장점이 있지만, Excel이 설치된 Windows(또는 macOS)가 필요합니다. 그런데 GitHub이 제공하는 Windows runner에는 Excel이 설치되어 있지 않아 xlwings가 실패하고, 변환기가 openpyxl로 자동 대체합니다(로그에 경고로 표시). 진짜 Excel로 읽으려면 Excel이 설치된 self-hosted runner가 필요해요. 이번 실습은 일부러 이 구조를 택해 Actions의 OS 선택을 경험해 보고, 마지막 장에서 "실무라면 Linux에서 병렬로 처리하는 게 왜 더 나은지" 비교합니다.

🏁 마무리: 오늘 만들 서비스의 큰 그림

이 장에서는 코드를 쓰지 않고, 앞으로 Step 1~6에서 만들 서비스의 전체 지도를 그렸습니다. 서버 없이 GitHub 기능 네 가지(Repository · Issues · Actions · Pages)를 조합해 "엑셀 업로드 → 자동 변환 → 웹 대시보드"를 만든다는 것이 핵심이에요.

💡 이 장에서 이해한 것

전체 구조
① 이슈에 엑셀 첨부 → ② Actions의 Windows runner(실제 VM)가 변환 → ③ 봇이 docs 브랜치에 커밋 → ④ Pages가 대시보드로 공개.
왜 이런 구조인가
업로드 창구·처리 서버·데이터베이스·웹 서버를 각각 Issues·Actions runner·Git 커밋·Pages가 대신 맡아요. 평소엔 아무것도 돌지 않고, 이벤트가 생길 때만 일합니다.
main과 docs
main은 사람이 고치는 소스 코드, docs는 봇이 만드는 배포 결과물(data/data.json 포함). 브랜치를 용도별로 나눠 씁니다.
Windows + xlwings
실제 Excel을 조종하는 방식을 경험하려고 일부러 고른 구조예요. 단, GitHub의 Windows runner에는 Excel이 없어 실제 변환은 openpyxl로 대체됩니다. 실무에서 더 나은 방법은 한계 장에서 비교합니다.
최종 저장소 구조
.github/(이슈 양식·워크플로우 4개), scripts/(변환·다운로드·배포), dashboard/(화면), tests/, CLAUDE.md. 막히면 templates/excel-dashboard/와 비교하세요.

🔍 확인하고 넘어가기

  • 이슈 등록부터 대시보드 표시까지 4단계 흐름을 그림 없이 말할 수 있다
  • runner가 job마다 새로 만들어지고 끝나면 폐기되는 실제 VM이라는 것을 이해했다
  • main과 docs 브랜치에 각각 무엇이 들어가는지 구분할 수 있다
  • 비밀번호 화면이 "진짜 보안"인지 의심해 볼 거리가 있다는 것을 기억해 두었다
