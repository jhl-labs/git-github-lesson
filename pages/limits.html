한계와 다음 단계

오늘 만든 서비스는 동작합니다. 하지만 "동작한다"와 "안전하다·운영할 만하다"는 다릅니다. 이 장에서는 우리 구조의 약점을 직접 공격해 보고, 실무라면 어떻게 바꿔야 하는지 정리합니다.

한계 1 · 그 비밀번호는 보안이 아닙니다

우리 로그인은 브라우저 안의 JavaScript가 "해시가 같으면 화면을 보여준다"는 판단을 할 뿐이에요. 브라우저는 사용자의 것이고, 사용자는 그 판단을 언제든 바꿀 수 있습니다. 직접 해 봅시다.

공격 ① 로그인 화면 우회 & 데이터 직접 열기

공격 ② 해시를 보고 비밀번호 알아내기

config.js는 공개 파일이라 해시가 누구에게나 보입니다. SHA-256은 거꾸로 풀 수는 없지만, 후보를 하나씩 해시해서 비교하면 됩니다(무차별 대입). 아래는 지금 이 브라우저 한 탭이 실제로 해 보는 겁니다.

정리: 무엇이 문제인가

약점설명
데이터가 공개 파일data/data.json은 주소만 알면 비밀번호 없이 받을 수 있어요. 공개 저장소라면 GitHub에서 docs 브랜치를 열어 봐도 됩니다.
판단을 클라이언트가 함sessionStorage 값 하나만 바꾸면 로그인 상태가 됩니다. 서버가 검증하지 않으면 인증이 아니에요.
해시가 공개됨소금(salt)도, 느린 해시(bcrypt·Argon2)도 없는 SHA-256은 초당 수십억 번(GPU) 시도할 수 있어요.
원본 엑셀도 공개공개 저장소의 이슈 첨부 파일은 누구나 내려받을 수 있습니다. 엑셀 원본이 그대로 노출돼요.
Git은 잊지 않는다잘못 올린 데이터를 지워도 커밋 이력에 남습니다. 완전히 지우려면 이력 재작성이 필요하고, 이미 누군가 clone 했다면 회수 불가.
사용자 구분 없음비밀번호 하나를 모두가 공유 → 누가 봤는지 모르고, 한 명이 퇴사해도 비밀번호를 바꾸는 것 외엔 방법이 없어요.
"그럼 데이터를 암호화해서 올리면요?" 좋은 발상이에요. 워크플로우에서 비밀번호로 data.json을 AES로 암호화하고 브라우저에서 복호화하면(StatiCrypt 같은 방식) 공격 ①은 막힙니다. 하지만 여전히 암호문은 공개되어 있어 오프라인 무차별 대입(공격 ②)이 가능하고, 비밀번호 공유·폐기·권한 구분 문제는 그대로입니다. "정적 사이트에 비밀을 올려도 되는가?"의 답은 결국 "아니오"입니다.

한계 2 · 그래서 진짜 백엔드 서버가 필요합니다

백엔드 서버는 사용자가 손댈 수 없는 곳에서 판단하고, 허락된 데이터만 내보내는 문지기입니다.

필요한 것정적 사이트(오늘)백엔드 서버
인증 (누구인가?)❌ 흉내만✅ 서버가 비밀번호/SSO 검증, 세션·토큰 발급

그럼 오늘 구조는 언제 써도 될까? 공개되어도 괜찮은 데이터(사내 공지 통계, 오픈 데이터, 개인 포트폴리오 등)라면 훌륭한 선택입니다. 또는 GitHub Enterprise의 Private Pages처럼 플랫폼이 접근 제어를 대신해 주는 경우에 한해 내부 데이터를 다룰 수 있어요. 매출·개인정보처럼 비밀이어야 하는 데이터라면 백엔드(또는 인증을 제공하는 플랫폼)가 반드시 필요합니다.

한계 3 · Windows runner보다 Linux 병렬이 더 가치 있다

우리가 Windows를 쓴 이유는 단 하나, xlwings(=Excel 앱)를 쓰기 위해서였어요. 그런데 GitHub이 제공하는 Windows runner에는 Excel이 설치되어 있지 않아 결국 openpyxl로 대체되었죠. 진짜 Excel을 쓰려면 Office가 설치된 self-hosted Windows runner를 직접 운영해야 하고, 라이선스와 서버 관리 부담이 생깁니다.

Windows + xlwingsLinux + openpyxl/pandas
Runner 준비 시간길다 (Windows 부팅, 무거운 이미지)짧다
과금 (private 저장소, 무료 사용량 초과 시)분당 $0.010 (2코어, 작성 시점) — Linux의 약 1.7배분당 $0.006 (2코어)

엑셀 파일이 여러 개라면 차이는 더 커집니다. 슬라이더를 움직여 보세요. (시간 값은 설명을 위한 예시 가정치이고, 실제 단가는 GitHub Actions 요금 문서를 확인하세요.)

Linux 병렬 버전 워크플로우 맛보기

strategy.matrix를 쓰면 같은 Job을 입력만 바꿔 동시에 여러 개 실행합니다.

jobs:
  convert:
    runs-on: ubuntu-latest            # 빠르고 저렴한 Linux
    strategy:
      max-parallel: 10
      matrix:
        file: [seoul.xlsx, busan.xlsx, daegu.xlsx, gwangju.xlsx, daejeon.xlsx]
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with: { python-version: "3.12", cache: pip }
      - run: pip install openpyxl
      - run: python scripts/excel_to_json.py "data/${{ matrix.file }}" --engine openpyxl --out "build/${{ matrix.file }}.json"
      - uses: actions/upload-artifact@v6
        with: { name: "json-${{ matrix.file }}", path: build/, retention-days: 1 }

  publish:                            # 모든 변환이 끝나면 한 번만 합쳐서 배포
    needs: convert
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v7
      # ... JSON 합치기 → docs 브랜치에 push

  deploy:                             # GITHUB_TOKEN push로는 Pages가 갱신되지 않으니 배포 워크플로우 호출
    needs: publish
    permissions: { contents: read, pages: write, id-token: write, actions: read }
    uses: ./.github/workflows/pages-deploy.yml
핵심 메시지 CI/CD의 가치는 "자동으로 돈다"가 아니라 "빠르고, 싸고, 똑같이, 동시에 많이" 돈다는 데 있습니다. 특정 OS·GUI 앱에 묶이면 그 장점을 대부분 잃어요. 엑셀 처리라면 Linux + 파이썬 라이브러리 + matrix 병렬이 기본값이고, Excel 앱이 꼭 필요한 예외만 self-hosted Windows로 분리하세요.
