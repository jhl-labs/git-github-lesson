GitHub Pages 깊이 알기

PART 2에서는 Source를 "GitHub Actions"로 고르고 워크플로우가 docs 브랜치 내용을 배포하자 대시보드가 인터넷에 올라갔습니다. 이 장에서는 그 버튼 뒤의 빌드·배포 과정, 사이트 종류와 주소 규칙, 커스텀 도메인과 HTTPS, 캐시, 한도, 보안, 그리고 Pages로 할 수 없는 일까지 정리합니다.

(참고) 실습에 꼭 필요하지는 않지만… PART 3은 선택 학습 자료입니다. 실습은 PART 2의 설정만으로 충분하지만, 내 도메인을 연결하거나 "왜 수정한 게 바로 안 보이지?", "왜 새로고침하면 404지?" 같은 문제를 만났을 때 이 장이 도움이 됩니다. 한도·플랜 관련 숫자는 작성 시점(2026년 11월) 기준이니 링크된 공식 문서로 최신 값을 확인하세요.

1. GitHub Pages란 무엇인가

GitHub Pages는 저장소의 파일을 정적 웹사이트로 내보내는 호스팅 서비스입니다. 배포된 파일은 GitHub의 CDN(전 세계에 분산된 캐시 서버) 앞단에서 서빙되어, 어느 나라에서 접속해도 가까운 서버가 응답합니다.

정적 호스팅
요청 URL에 대응하는 파일을 그대로 반환. 사용자·요청 내용에 따라 응답이 바뀌지 않음
CDN
Content Delivery Network. 원본 파일을 여러 지역의 캐시 서버에 복사해 빠르게 전달. 대신 갱신이 바로 퍼지지 않을 수 있음
Publishing source
Pages가 사이트 파일을 가져오는 곳. "브랜치+폴더" 또는 "GitHub Actions"
github-pages 환경
Pages 배포 기록이 남는 deployment environment. 저장소 오른쪽 "Deployments"에서 이력 확인

3. 게시 방식: 브랜치 vs GitHub Actions

Settings → Pages → Build and deployment → Source에서 두 가지 중 하나를 고릅니다.

Deploy from a branchGitHub Actions
원리지정한 브랜치의 /(root) 또는 /docs 폴더를 그대로(또는 Jekyll로 빌드해) 게시워크플로우가 만든 Pages artifact(tar)를 배포
빌드GitHub의 Jekyll 빌드만 가능 (플러그인 허용 목록 제한)Vite, Hugo, Next.js export, Jekyll 최신 버전 등 무엇이든
산출물 커밋필요 (게시할 파일이 브랜치에 있어야 함)불필요. 저장소 이력이 깨끗함 (PART 2는 데이터 변경 이력을 남기려고 결과물을 일부러 docs 브랜치에 커밋한 뒤, 그 브랜치를 Actions로 배포)
배포 트리거그 브랜치에 push될 때마다 자동. 단, GITHUB_TOKEN으로 push한 커밋은 빌드를 시작하지 않음워크플로우의 on:로 자유롭게
CNAME 파일설정에서 도메인을 넣으면 브랜치에 커밋됨사용 안 함 (설정 화면 값이 기준)
빌드 횟수 soft limit시간당 10회적용 안 됨
어울리는 곳빌드가 없는 순수 HTML, 문서, 간단한 Jekyll 블로그빌드 도구가 필요한 프로젝트, 산출물을 커밋하고 싶지 않을 때

"pages build and deployment" 워크플로우

"Deploy from a branch"를 선택해도 내부적으로는 Actions가 돕니다. 브랜치에 push가 일어나면 Actions 탭에 pages build and deployment라는 자동 생성 워크플로우가 나타나 build(Jekyll 또는 그냥 복사) → deploy 순으로 실행돼요. 저장소에 YAML 파일이 없는데도 실행 기록이 보이는 이유입니다. 배포가 실패하면 이 실행의 로그부터 확인하세요.

PART 2와 연결 공식 문서에 따르면 워크플로우가 GITHUB_TOKEN으로 push한 커밋은 Pages 빌드를 트리거하지 않습니다. 그래서 PART 2는 "Deploy from a branch"를 쓰지 않고, 봇이 docs 브랜치에 커밋한 뒤 같은 실행 안에서 재사용 워크플로우 pages-deploy.yml(upload-pages-artifact → deploy-pages)을 호출해 직접 배포합니다. PAT(개인 토큰)로 push해 빌드를 일으키는 방법도 있지만, 오래 사는 비밀을 관리해야 하므로 권하지 않아요.

GitHub Actions로 직접 배포하기

# .github/workflows/pages.yml
name: Deploy Pages

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write        # Pages 배포
  id-token: write     # 배포 요청의 출처를 OIDC로 증명

concurrency:
  group: pages
  cancel-in-progress: false   # 배포 도중에 끊지 않기

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with: { node-version: "22", cache: npm }
      - run: npm ci && npm run build          # 결과물이 dist/ 에 생긴다고 가정
      - uses: actions/configure-pages@v6
      - uses: actions/upload-pages-artifact@v5
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v5
  • 빌드 Job과 배포 Job을 나누면, 배포 Job만 pages: write를 갖도록 Job 단위 권한으로 더 좁힐 수 있습니다.
  • github-pages environment에는 기본적으로 "배포 가능한 브랜치" 규칙이 걸립니다. 다른 브랜치에서 배포하려다 거절되면 Settings → Environments → github-pages를 확인하세요.
  • upload-pages-artifact는 v4부터 숨김 파일(dotfile)을 기본 제외합니다(그래서 PART 2의 .nojekyll도 실제로는 올라가지 않지만, Actions 배포에선 필요 없으므로 문제없습니다). .well-known/ 같은 경로가 필요하면 include-hidden-files: true 입력을 쓰세요(.git·.github는 항상 제외).
  • 예시의 버전 태그는 작성 시점 기준입니다. 실무에서는 각 Action의 최신 릴리스를 확인하고 커밋 SHA로 고정하세요(Actions 깊이 알기 8절).

4. Jekyll 처리와 .nojekyll

브랜치 게시 방식에서 Pages는 기본적으로 파일을 Jekyll(Ruby 정적 사이트 생성기)로 처리합니다. 순수 HTML 사이트라도 Jekyll을 거치기 때문에 다음 규칙이 적용돼요.

Jekyll 규칙영향
_로 시작하는 파일·폴더는 무시_app/, _next/, _assets/ 같은 빌드 산출물 폴더가 통째로 404
.으로 시작하거나 ~로 끝나는 파일 무시설정 파일·백업 파일이 게시되지 않음
front matter(---)가 있는 파일은 템플릿으로 변환Markdown → HTML, Liquid 문법 해석
Liquid 문법 해석문서 안의 {{ }}, {% %}가 의도치 않게 처리될 수 있음
_config.yml의 include/exclude무시 규칙 예외 지정 가능

Jekyll이 필요 없다면 게시 폴더 최상단에 빈 .nojekyll 파일을 두세요. 처리 단계가 생략되어 파일이 있는 그대로 게시되고 빌드도 빨라집니다. (Actions 게시 방식에서는 Jekyll이 돌지 않으므로 필요 없습니다. PART 2의 publish_docs.sh가 만드는 .nojekyll은 브랜치 게시로 바꿔도 안전하도록 남겨 둔 것이에요.)

touch .nojekyll
git add .nojekyll && git commit -m "Jekyll 처리 끄기"

CNAME 파일 vs 설정 화면

  • 브랜치 게시: Settings → Pages → Custom domain에 입력하면 GitHub이 게시 브랜치에 CNAME 파일(도메인 한 줄)을 커밋합니다. 봇이 게시 브랜치를 통째로 다시 만드는 구조라면 이 파일이 지워져 도메인 연결이 풀릴 수 있으니, 배포 스크립트가 CNAME을 보존·생성하게 하세요.
  • Actions 게시: CNAME 파일은 무시되고 설정 화면의 값만 사용됩니다.

도메인 탈취(takeover) 막기

DNS는 남아 있는데 Pages를 껐다면? www.example.com이 아직 you.github.io를 가리키는데 저장소를 지우거나 Pages를 끄면, 다른 GitHub 사용자가 그 도메인을 자기 저장소에 연결해 여러분 도메인으로 콘텐츠를 띄울 수 있습니다.
  • 계정·조직 설정의 Pages → Verified domains에서 도메인을 검증하세요(_github-pages-challenge-<계정> TXT 레코드). 검증된 도메인은 다른 계정이 쓸 수 없습니다.
  • *.example.com 같은 와일드카드 DNS 레코드는 쓰지 마세요. 검증을 해도 하위 서브도메인 탈취 위험이 남습니다.
  • 사이트를 내릴 때는 DNS 레코드부터 정리하세요.

6. HTTPS

  • *.github.io 주소는 처음부터 HTTPS이며, 브라우저 HSTS preload 목록에 있어 HTTP로 접속할 수 없습니다.
  • 커스텀 도메인은 DNS가 올바르게 설정되면 GitHub이 Let's Encrypt 인증서를 자동 발급합니다. 발급에는 시간이 걸릴 수 있고, 그동안 "Enforce HTTPS" 체크박스가 비활성화되어 있어요.
  • 발급이 완료되면 Enforce HTTPS를 켜서 HTTP 요청을 HTTPS로 리다이렉트하세요.
  • 도메인에 CAA 레코드가 있다면 letsencrypt.org를 허용해야 인증서가 발급됩니다.
  • Cloudflare 같은 프록시를 앞에 두면(주황 구름) GitHub이 도메인 소유를 확인하지 못해 인증서 발급이 실패할 수 있습니다. 처음엔 DNS only로 발급받는 편이 안전합니다.

7. 캐시와 CDN: "왜 바로 안 바뀌죠?"

Pages 응답에는 짧은 캐시 헤더가 붙습니다. 작성 시점에 관찰되는 값은 Cache-Control: max-age=600(10분)이며, 이 값은 사용자가 바꿀 수 없습니다.

curl -sI https://you.github.io/excel-dashboard/data/data.json | grep -iE "cache-control|age|etag|last-modified"
지연 원인설명대응
배포 워크플로우 진행 중push 후 build·deploy에 수십 초~수 분 (PART 2 실측: Pages deploy Job 약 15초, 이슈 등록부터 반영까지 약 1~2분)Actions 탭·Deployments에서 완료 확인
CDN 캐시엣지 서버가 이전 파일을 잠시 들고 있음몇 분 기다리기. 사용자에게 강제할 방법은 없음
브라우저 캐시max-age 동안 브라우저가 재요청하지 않음강력 새로고침, 개발자 도구의 "Disable cache"
캐시를 우회하는 정석: 파일 이름이나 쿼리에 버전 넣기 빌드 도구는 app.3f9a1c.js처럼 내용 해시를 파일명에 넣어(cache busting) 바뀐 파일이 항상 새 주소가 되게 합니다. 빌드 도구가 없다면 fetch('data/data.json?v=' + Date.now(), { cache: 'no-store' })처럼 데이터 요청에만 쿼리를 붙이는 방법도 있습니다. 다만 CDN이 이미 들고 있는 HTML 자체는 몇 분간 이전 버전일 수 있어요.

9. SPA 라우팅

React·Vue 같은 SPA는 /dashboard/sales 같은 주소를 브라우저 안에서 JavaScript가 처리합니다. 그런데 사용자가 그 주소로 직접 접속하거나 새로고침하면, Pages는 dashboard/sales라는 파일을 찾다가 없으니 404를 돌려줍니다. 서버에 "모든 경로를 index.html로" 같은 rewrite 규칙을 넣을 수 없기 때문이에요.

방법원리장단점
Hash 라우팅/#/sales처럼 # 뒤는 서버로 가지 않음가장 단순·확실. 주소가 덜 예쁘고 SEO에 불리. (이 학습 사이트가 쓰는 방식)
404.html 트릭Pages는 없는 경로에 404.html을 보여줌 → 그 안의 스크립트가 원래 경로를 쿼리로 바꿔 index.html로 리다이렉트깔끔한 주소. 하지만 첫 응답 상태가 404라 검색엔진·모니터링에 불리, 리다이렉트 한 번 추가
사전 렌더링(SSG)경로마다 sales/index.html을 빌드 시 생성SEO·속도 최고. 경로가 빌드 시점에 정해져야 함
 
# 가장 간단한 404 대응: 빌드 결과의 index.html 을 404.html 로도 복사
cp dist/index.html dist/404.html   # 상태 코드는 여전히 404 라는 점에 유의

Project 사이트라면 라우터와 빌드 도구에 base path(/excel-dashboard/)를 알려 줘야 합니다. 예: Vite base: '/excel-dashboard/', React Router basename.

10. Pages로 할 수 없는 것

하고 싶은 것Pages에서대안

커스텀 HTTP 헤더 (CSP, HSTS 설정, CORS 등)불가일부는 <meta> 태그로, 나머지는 CDN 프록시 앞단에서
리다이렉트·rewrite 규칙불가 (Jekyll redirect 플러그인의 HTML 리다이렉트 정도)meta refresh, JS 리다이렉트, 다른 호스팅
폼 제출 처리불가외부 폼 서비스, GitHub 이슈 폼(PART 2처럼)
환경 변수·secret불가 (빌드 시 넣으면 파일에 그대로 노출)비밀은 서버에만

CSP는 meta 태그로

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' https://cdn.jsdelivr.net; img-src 'self' data:; connect-src 'self'">

meta 태그 CSP는 <head> 맨 앞쪽에 두어야 하며, frame-ancestors, report-uri, sandbox 지시어는 meta에서 동작하지 않습니다. 클릭재킹 방지(frame-ancestors, X-Frame-Options)가 꼭 필요하면 헤더를 넣을 수 있는 호스팅이나 프록시가 필요합니다.

11. 보안 관점에서 다시 보기

게시된 것은 전부 공개다 게시 브랜치(또는 artifact)에 들어간 파일은 링크가 걸려 있지 않아도 주소만 알면 누구나 받을 수 있습니다. 브랜치 게시라면 공개 저장소에서 그 브랜치의 커밋 이력까지 열람 가능하고, 삭제해도 이력에 남습니다.
  • PART 2의 data/data.json과 config.js의 비밀번호 해시가 바로 이 경우입니다. 로그인 화면은 "보이는 것"만 가릴 뿐, 한계 장에서 본 것처럼 데이터 파일은 직접 열 수 있어요.
  • robots.txt나 "주소를 아무에게도 안 알려 줌"은 접근 제어가 아닙니다. 검색엔진이 안 긁어 갈 뿐(그마저도 보장되지 않음), 공격자는 신경 쓰지 않습니다.
  • 빌드 시 환경 변수로 API 키를 넣는 SPA 패턴(VITE_API_KEY 등)은 결과 JS에 키가 평문으로 박힙니다. 공개되어도 되는 키(공개용 지도 키 등, 도메인 제한 설정)만 넣으세요.
  • 사용자 입력·외부 데이터를 화면에 그릴 때 textContent를 쓰는 습관(PART 2 대시보드)은 정적 사이트에서도 XSS를 막는 핵심입니다. 같은 you.github.io 오리진의 다른 Project 사이트와 localStorage를 공유한다는 점도 기억하세요.
  • CDN 스크립트에는 SRI(integrity)를 붙여 CDN이 변조되어도 실행되지 않게 하세요(PART 2의 Chart.js처럼).

Team 플랜의 private 저장소에서 Pages로 사내 매출 대시보드를 게시했습니다. 외부인이 데이터를 볼 수 있을까요?

정답! 사이트 접근 제어(private Pages)는 작성 시점 기준 Enterprise Cloud 조직에서만 제공됩니다. 그 외에는 비밀 데이터를 Pages에 올리면 안 됩니다.

12. SEO 기초

  • 페이지마다 고유한 <title>과 <meta name="description">
  • <html lang="ko">, 의미 있는 제목 구조(h1→h2)
  • 공유 미리보기용 Open Graph 태그(og:title, og:image)
  • sitemap.xml과 robots.txt를 사이트 루트에 (Project 사이트는 /repo/ 아래라는 점 주의: 도메인 루트의 robots.txt는 User 사이트가 결정)
  • 같은 콘텐츠가 여러 주소에 있으면 <link rel="canonical">
  • Hash 라우팅·클라이언트 렌더링은 검색 노출에 불리 → 중요한 페이지는 정적 HTML로
  • Google Search Console 소유 확인은 meta 태그 또는 DNS TXT로 (커스텀 도메인이면 DNS 방식이 편함)
  • Jekyll을 쓴다면 jekyll-seo-tag, jekyll-sitemap 플러그인(GitHub Pages 허용 목록에 포함)
