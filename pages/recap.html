실습 돌아보기

여기까지 왔다면 엑셀 한 장이 진짜 GitHub 위에서 이슈 → 자동화 → 커밋 → 웹 대시보드로 흘러가는 서비스를 직접 만든 거예요. 무엇을 했고, 무엇을 배웠는지 한 페이지로 정리해 봅시다.

한 번의 업로드에서 실제로 일어난 일

Step 5에서 이슈 하나를 등록했을 때, 화면 뒤에서는 아래 일들이 순서대로 일어났습니다.

  1. 이슈 등록 이슈 폼에 엑셀을 끌어다 놓자 GitHub이 파일을 보관하고, 본문에 user-attachments 첨부 링크를 넣었어요.
  2. 이벤트 발생 GitHub이 issues: opened 이벤트와 이슈 정보(JSON 페이로드)를 만들어, on: issues로 기다리던 워크플로우를 깨웠어요.
  3. 조건 확인 먼저 Linux gate job이 제목의 [EXCEL]과 (권한 API로) 작성자의 저장소 권한을 검사해 "실행해도 되는 요청"인지 걸렀어요.
  4. 실제 Windows 서버 준비 GitHub이 클라우드에 이 job 전용 Windows Server VM을 새로 만들고, actions/checkout으로 저장소 코드를 내려받았어요.
  5. 엑셀 읽기 그 서버에서 파이썬이 첨부 파일을 내려받아 검사(도메인·크기·ZIP 서명)한 뒤, xlwings를 시도하고 Excel이 없어 openpyxl로 대체해 읽었어요.
  6. JSON 생성 행·열·타입·합계를 담은 build/data.json을 만들었어요.
  7. 봇 커밋 github-actions[bot]이 GITHUB_TOKEN으로 docs 브랜치에 data/data.json을 커밋·push하고, 이슈에 결과 댓글을 단 뒤 닫았어요. job이 끝나자 VM은 폐기됐어요.
  8. Pages 배포 같은 실행의 deploy job이 pages-deploy.yml을 불러 docs 브랜치 내용을 GitHub Pages에 배포했어요. (봇이 GITHUB_TOKEN으로 push한 커밋은 Pages 빌드를 스스로 시작하지 않기 때문)
  9. 브라우저 팀원이 주소에 접속하면 브라우저가 HTML·JS를 받고, fetch()로 data.json을 가져와 차트와 표를 그렸어요.
  10. 로그인 화면 입력한 비밀번호를 브라우저에서 SHA-256으로 해시해 비교하고, 맞으면 sessionStorage에 표시해 대시보드를 보여줬어요. (화면만 가리는 학습용 장치!)

GitHub 기능이 이 프로젝트에서 맡은 역할

📁

Repository

소스 코드(main)와 배포 결과물(docs)을 브랜치로 나눠 보관. 데이터 변경 이력도 커밋으로 남았어요.

🐛

Issues

엑셀 업로드 창구이자 자동화의 방아쇠. 결과 알림(봇 댓글)도 여기로 돌아왔어요.

⚙️

Actions

이벤트가 생길 때만 실제 서버를 띄워 변환·배포·리뷰를 실행한 일꾼.

🌐

Pages

docs 브랜치의 파일을 HTTPS 웹사이트로 공개한 정적 호스팅.

🔀

Pull Request

합치기 전에 diff를 보여주고 사람·AI 리뷰를 받는 관문.

🔑

Secrets · GITHUB_TOKEN

API 키는 Secret으로, 저장소 쓰기는 최소 권한의 임시 토큰으로 처리했어요.

바이브 코딩, 이렇게 했어요

  1. 프롬프트 목표 · 입력/출력 형식 · 설계 · 보안 규칙 · 테스트까지 구체적으로 적었어요. 공통 규칙은 CLAUDE.md에 한 번만.
  2. diff 리뷰 Claude가 바꾼 내용을 읽고, innerHTML·${{ }} 직접 삽입 같은 위험 신호를 확인했어요.
  3. 실행 테스트(pytest)·로컬 서버·실제 이슈 업로드로 "진짜 동작하는지" 확인했어요. 실패하면 로그를 그대로 AI에게 보여줬죠.
  4. 커밋 확인이 끝난 단위마다 커밋해 언제든 돌아갈 지점을 만들었어요. 협업이 필요한 변경은 PR로.
✦ 핵심 한 줄 AI가 코드를 쓰는 속도는 빨라졌지만, 무엇을 만들지 정하고 결과가 맞는지 판단하는 일은 여전히 사람의 몫이에요. 오늘 배운 이론이 그 판단의 기준입니다.

셀프 체크

아래 항목을 다른 사람에게 말로 설명할 수 있다면 체크하세요.

  • Git과 GitHub의 차이, 그리고 commit과 push의 차이
  • GitHub-hosted runner가 어디서 어떻게 만들어지고, job이 끝나면 어떻게 되는지
  • 워크플로우의 event · job · step · runner의 관계
  • 이슈 제목·본문을 run:에 직접 넣으면 안 되는 이유와 안전한 전달 방법
  • permissions:와 GITHUB_TOKEN, Secret의 역할
  • xlwings와 openpyxl의 차이, runner에서 openpyxl로 대체된 이유
  • main과 docs 브랜치를 나눈 이유
  • GitHub Pages가 "정적" 호스팅이라는 말의 의미
  • 비밀번호 화면이 진짜 보안이 아닌 이유 (해시 ≠ 암호화, data.json 직접 접근)
  • PR의 흐름과 squash merge의 결과
  • AI 코드 리뷰의 장점과 한계
